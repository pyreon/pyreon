### Core micro-benchmarks (`scripts/bench/`)

Bench-harness lesson: NO forced GC in bun/JSC micro-benches (`Bun.gc(true)` jettisons compiled code → re-tier noise; pooled small samples across process spawns instead); **state-tree** vs MST — faster on the action/patch/reactive hot path; **machine** vs XState — large constant-factor win on common ops (XState buys statechart features Pyreon offloads to signals); **i18n** vs i18next — faster on every op (`Intl.PluralRules` memoized per locale — the bench caught a ~16× plural regression); **permissions** vs CASL; **form** vs TanStack form-core; **query** vs `@tanstack/react-query` (`bench:react-query`, real react-dom@19 in happy-dom) — both wrap the SAME `@tanstack/query-core` (pinned tree-wide), so it measures the ADAPTER not the engine; the HEADLINE is a deterministic COUNT: on a data-ONLY change (`setQueryData`), an INTRA-component reader of 8 fields re-runs **1 field-derivation + 0 component re-runs** (Pyreon signal-granular) vs react-query's **8 derivations + 1 whole-component re-render + VDOM reconcile** (observer=component granularity); CROSS-component (one reads `status`, one `data`) is a **🤝 tie** — react-query's tracked-props ARE field-aware across components, so the honest win is INTRA-component + steady-state per-update latency (~4× on data-flip→DOM: synchronous fine-grained patch vs react-query's macrotask-batched render), NOT mounting (~tied) and NOT cross-component. ns is machine-dependent — the ratio is the portable signal.

**SSR throughput harness (`bench:ssr`) — fixed 2026-07, was unusable.** `scripts/bench/core/runtime-server.ts` never forced `NODE_ENV=production`, so it timed the DEV build: dev's always-on reactive-devtools registry accumulates across the ~30k renders in a 3s window until the run collapses into GC pressure. Measured `links-100` across three consecutive runs of IDENTICAL code: **108 / 10,578 / 195 renders/sec (98x spread)**; under production the same cell reads **12,272 / 11,194 / 12,296 (1.1x)** — so the old harness could understate Pyreon ~100x AND manufacture a later "improvement" out of noise. It also used ONE timed window with a fixed 50-render warmup (~0.3ms for `empty` vs ~5ms for `links-100` — systematically under-warming the cheap cells) and no correctness gate. Now: self-re-exec guard forcing production before any value import (ESM hoists static imports above a top-level assignment — the same trap `ssr-crossframework.ts` documents), pooled windows + median + 95% bootstrap CI with a `~noisy` flag when the CI half-width exceeds 10% of the median, adaptive warmup, randomized scenario order, and a correctness gate (bisect-verified: a wrong expectation exits 1). Post-fix `links-100` is 11,766 / 11,916 / 11,525 across runs (1.03x). NOTE this file is **Pyreon-only** and is NOT a competitive comparison — cross-framework SSR numbers come from `bench:ssr-cross`, which renders the same tree through React/Preact/Solid behind a byte-identical correctness gate.

**The addressable ceiling on bulk-create (measured 2026-07, Chromium-isolated).** Before spending more effort on the `create 10,000` gap, know what is even reachable. Decomposing the op in real Chromium with one stage isolated per variant (`scripts/bench/dom-micro.ts`, 11 pooled samples, interleaved + order-reversed, CI95): **cloneNode only 7.3ms/10k · + set row text 10.2ms · + live insert with forced layout 147.7ms**. So the JS a framework CONTROLS is ~7% of the operation and **~93% is browser insert + layout**, identical for every framework. Pyreon's entire measured overhead vs Vanilla on that op is 3.2ms of ~95ms (3.4%) — i.e. already a fraction of a ~7% envelope. Making ALL Pyreon JS on that path free would win ~3.4%; the individual levers left are ~0.15% each (see the declined list below). **Do not read a create-op regression/win under ~0.5% as real** — that is inside the macro suite's own run-to-run spread (95.10 / 95.50ms across two idle runs). Corollary: further bulk-create micro-optimisation is not where remaining headroom lives; the unmeasured territory is the real-app head-to-head that does not exist yet (see the benchmark section's honest limits).

**Declined micro-optimizations (measured 2026-07, negative — do NOT re-try):** three hot-path hypotheses were A/B'd on JSC with pooled medians and all three found the CURRENT code already optimal. (1) *Sole-subscriber extraction* — `subs.values().next().value` is the FASTEST form at 5.71ns; `for…of`+break is 8.09ns (1.4×) and `Set.forEach` 17.82ns (3.1×), so the residual chain/diamond cost is inherent to `Set` subscriber storage, not the extraction. (2) *Hoisting `Set.prototype.size`* in `notifySubscribers` (read up to 3× per call) — no measurable delta at 1/4/100 subscribers; JSC already folds the getter. (3) *Replacing `Object.is`* in `_set`'s equality gate with an inlined `a===b ? a!==0||1/a===1/b : a!==a&&b!==b` — SLOWER (6.39 vs 5.38ns on ints); `Object.is` is intrinsified. Harnesses: `/tmp` A/B scripts in PR #2502.

**[SHIPPED 2026-08] COMPONENT CHILDREN as `_ssr` holes — the largest remaining eligibility lever, and the one that took two attempts.** A DOM wrapper holding a component child used to be declined outright, so `<main class="m"><Widget /></main>` — the shape of essentially every layout wrapper — emitted ZERO `_ssr` and the bail compounded with nesting depth. It now templates. **The first attempt emitted the component as a plain hole and was reverted: it passed EVERYTHING at unit level and still broke 26 ui-showcase specs.** Root cause is structural: an `_ssr(...)` hole is an EAGERLY-EVALUATED function argument, which matches h() for a hole that reads a VALUE but not for one that RENDERS a component — rendering has context side effects and h() defers it. For `<Provider theme={t}><div class="page"><Consumer /></div></Provider>` the eager emit ran `Consumer` while Provider's CHILDREN ARGUMENT was still being built, before `provide()` had pushed anything, so every context read returned the default (`Cannot read properties of undefined (reading 'system')` out of rocketstyle's `getThemeFromChain`). **The fix defers the CALL, not the hole:** the compiler emits `_ssrDeferred(() => _ssr(...))` and `renderNode`/`streamNode` invoke the thunk exactly where they would have rendered the equivalent vnode. Deferring the whole call is what makes it compose — a nested `_ssr` collapses into its parent's call and rides inside the same thunk, so no laziness propagates through `_ssrConcat`/`_ssrChildren`/`holeToString`; and `renderForItems` already routes rows through `renderNode`, so `<For>` item bodies are covered by the same branch. **The generalisable rule: a compile-to-string hole may contain a pure VALUE read, but never a RENDER with context side effects — unless the whole construct is deferred to its render position.** Position space, now covered by tests: a component's RETURN and a DOM-nested tree are safe either way (call site and render position coincide); COMPONENT-CHILDREN and MODULE-CONST are the load-bearing pair (bisect-verified — both render the context DEFAULT without the deferral); HELPER-CALL passes either way because the compiler already rewrites `{row()}` in a component child to a lazy accessor `{() => row()}`, while a bare identifier `{frag}` gets no such wrap.

**Why the unit gates could not have caught it, and what that cost.** Every byte-identity / hydration / native-equivalence / fuzz case rendered the `_ssr` node at TOP LEVEL — the single position where eager and deferred evaluation coincide. A differential oracle shaped as "render this node and compare bytes" structurally cannot express "...and now put it in a component's children." **And the e2e that caught it was, on current `main`, a false negative:** `ssrTemplate` is AUTO-enabled only when `@pyreon/runtime-server` resolves from the app, and no example declares it — verified against a fully-installed `main` checkout, where `examples/ui-showcase/node_modules/@pyreon/` contains only `core` and `ui-core`, and both bun's and Vite's node_modules walk come up empty for `runtime-server`. So the 26-spec gate was running with the compile-to-string path OFF, and would have stayed green against ANY change to it. Adding the dependency to the example turns it into a real gate (bisect: reverted to the eager emit → all 26 fail; restored → 26/26). **Two lessons worth generalising: a gate that only exercises the safe POSITION of a construct is not a gate for that construct; and before trusting a green e2e on a feature-flagged path, prove the flag was ON — resolvability-gated auto-enable is invisible in the test output.**

**The CLIENT `_tpl` path bails on self-closing roots too — and closing it is a NO-OP (measured 2026-08, do NOT "fix" it for symmetry).** After #2644 closed the SSR gate, the client template path still pre-gates self-closing roots out of `_tpl` (`tryTemplateEmit`), even though its own machinery handles them (`templateElementCount` returns 1, `processElement` emits `<tag attrs>` + a closing tag for non-void). It LOOKS like the identical oversight — same shape, no comment justifying it, no test asserting it — and the tempting move is to close it on class-symmetry grounds. **Measured first: it is a statistical tie.** Real Chromium, 10,000 single self-closing elements, 25 interleaved order-reversed runs, forced layout in the timed region, GC between: `cloneNode` off a cached `<template>` **22.10ms** vs `createElement` **22.30ms** — **1.01×**. The two gates are NOT the same class despite the same shape, because the MECHANISMS differ: `_ssr` replaces VNode allocation + a tree walk with string concatenation (a real 5–6× on `bench:ssr-cross`), whereas `_tpl`'s win is amortising a SUBTREE parse across instances — and a single self-closing element has no subtree, so it degenerates to `cloneNode` vs `createElement`, which is the same underlying DOM work. The client pre-gate is therefore harmless. **General lesson: "the same bug shape exists over there" is a hypothesis about the SHAPE, not about the WIN; two gates that look identical can sit on top of completely different cost models. Measure the second one before porting the fix.**

**Two more DOM-path leads triaged and declined (2026-08, profiled in real Chromium).** Both looked promising from the macro numbers and both die against the addressable ceiling above — recorded so the next person does not re-derive them. (1) *The per-row `NativeItem` wrapper in `_tpl`.* An allocation profile of `create 10,000` names `_tpl` the single biggest JS allocator at **33.9% (0.69 MB sampled)** — it returns a fresh `{ __isNative, el, cleanup }` per row, so 10k rows means 10k wrapper objects on top of the clone. Tempting, but it is one of the "~0.15% each" levers: the same profile is **43% `getBoundingClientRect` + 25.5% GC**, the gBCR being the harness's DELIBERATE forced layout (js-framework-benchmark methodology, inside the timed region), and `NativeItem` is a documented compiler↔runtime contract consumed by `mountChild`, `hydrateRoot` and the `<For>` path — high blast radius for a sub-0.5%-unmeasurable win. (2) *`clear rows` (Pyreon 300µs vs Octane 100µs, and slower than Vanilla's 200µs).* NOT DOM work: `handleFastClear` already detaches every row in ONE operation via a parent-clone `replaceChild`. The cost is the ~1,000 per-row reactive teardowns (`entry.cleanup()`), i.e. the price of fine-grained per-row reactivity, not a missing bulk-remove path. If this is ever worth attacking the target is teardown batching, not the DOM. **Reading for both: on a create/clear op, profile before optimising — the JS a framework controls is a single-digit percentage of the wall clock, and `getBoundingClientRect` dominating a profile here is the harness working correctly, not a bug.**

**SSR `h()`-path floor (measured 2026-07, Node profile).** After the env-gate fixes the remaining self-time is structural, not addressable: **renderChildList 18.6% · GC 16.4% · escapeHtml 10.0% · renderNode 9.3% · renderElement 9.0%**. Two hypotheses were tested and REJECTED — do not re-try. (1) *Replacing `acc += r` with an array join* in `renderChildList`: concat WINS at every size (4 children 49ns vs 132 join · 50 children **192ns vs 7050** · 500 children 1563 vs 8954), because V8 builds cons-strings/ropes rather than copying per `+=`. That also disproves the intuition that the adjacent GC comes from string building. (2) *Chasing the 16.4% GC*: it is **VNode allocation inherent to `h()`** — the 500-row fixture allocates ~2,002 VNode objects plus a props object each, PER RENDER. No `h()`-side change removes that; the compile-to-string `_ssr` path is the fix and already exists (5-6x faster on the same tree, see `bench:ssr-cross`). Practical consequence: further `h()`-path SSR micro-optimisation is not where headroom lives — widening `_ssr` ELIGIBILITY is.

**[CLOSED 2026-08 — #2515 (nested) + #2644 (root + item bodies)] The single biggest `_ssr` eligibility hole: SELF-CLOSING tags (measured 2026-07, structurally verified).** Both halves have now landed in BOTH backends: a nested `<img/>` no longer drops its enclosing component (#2515), and a component whose OWN body is self-closing (`<Icon> = () => <img …/>`, `<Divider>`, `<Input>`, `<Box> = () => <div …/>`) plus `.map`/`<For>` item bodies are eligible (#2644). Eligibility on the representative shapes went 2/6 → 6/6. A void element GIVEN explicit children still bails — genuinely ambiguous, the runtime drops the children. Two traps recorded for whoever widens eligibility next: (1) **`transformJSX` prefers the NATIVE backend**, so a JS-only edit measures as "no change" — and `bun run build` rebuilds only the JS lib, leaving the OLD `.node` binary in place; use `build:native`. (2) The parity test earns its keep: it caught a **latent JS-side dead `_ssrItem` import** (`buildSsrForItemBody` set `needsSsrItemImport` unconditionally while only emitting the fallback when a hole was not provably a string) that native never had. Historical description follows. `ssrSerializeElement` (`compiler/src/jsx.ts`) bails on `isSelfClosing(el)` — commented "rare" — but `<img />`, `<input />`, `<br />`, `<hr />` are in most real markup, and the bail is NOT local: it propagates up, so **one `<img/>` forces the whole enclosing component onto the `h()` path**. Verified by emit dump — a realistic card (`<article><div class=media><img src={props.src}/></div><div class=body>…</div></article>`) emits the outer `<article>` and the img branch as RAW JSX (h() path) and salvages only the void-free SIBLING `<div class=body>` into its own `_ssr(…)`. A grep for `_ssr(` in the output therefore FALSE-POSITIVES on this shape — assert on the ROOT element's emit, not on substring presence. The fix is small and the semantics are trivial (a self-closing VOID tag serializes as `<img …>`, a self-closing non-void as `<div></div>`); keep the separate `SSR_VOID_TAGS.has(tag)` bail (a void tag WITH children is genuinely ambiguous). Dual-backend: JS `ssrSerializeElement` + Rust `ssr_serialize_element` (lib.rs ~5424, ~5600) AND the root gate `ctx.ssr_template && !is_self_closing(el)` (~4287). Must ship with `native-equivalence` + `fuzz-equivalence` + byte-identical SSR output green. **Magnitude caveat (honest):** a synthetic A/B measured 97x, which is NOT trustworthy — the h() variant is async-promoted (a real Promise + microtask per render) while `_ssr` returns a string, so the harness compares two different execution models. The defensible figure is the validated `bench:ssr-cross` 5-6x; re-measure there after the widening, not with a bespoke harness.

**`process.env.NODE_ENV` is ~free in Bun and EXPENSIVE in Node (measured 2026-07).** A read costs **301ns in Node** vs 4.19ns hoisted (72x), but only **0.94ns in Bun** vs 0.35ns — Bun fast-paths it, Node's is a real getter over the environ. Two consequences. (1) An inline `process.env.NODE_ENV` dev gate on a PER-ITEM path is nearly free in Bun and in browser bundles (where a define folds it) but a real cost for an UNBUNDLED Node consumer — exactly the SSR deployment shape, since a Node server imports `lib/` directly with nothing to fold. A CPU profile of a 1,000-row `h()` SSR render attributed **36.7% of self-time** to `warnIfUnsafeTag`'s single inline gate; resolving it measured 1.65-2.75x on the whole render. (2) This is why Bun-run micro-benches CANNOT surface the cost — the reactivity bench reads 22.4M signal ops/s despite a per-write gate. **Profile SSR on Node, not Bun.** The fix that satisfies both consumers is a module-init TERNARY whose CONDITION is the bare inline expression (`const f = process.env.NODE_ENV === 'production' ? () => {} : realImpl`) — a define folds the condition, the ternary collapses to the no-op, and the dev-only branch tree-shakes. A `const __DEV__` alias does NOT fold (Bun.build keeps the strings) and is caught by `dev-gate-treeshake.test.ts`. Reactivity/runtime-dom keep inline gates deliberately: they are browser-bundled (folded) or Bun-run (free), so only genuinely-unbundled server paths warrant the ternary form.

Key reactivity optimizations: `_tpl()` (cloneNode), `_bind()` static-dep tracking, `TextNode.data` reactive text, single-subscriber inline slot (`_d1`) promoting to `Set` on 2nd subscriber, `_bindText` single-subscriber fast path, `_set` inline-batch direct dispatch (single-subscriber notify ~131ns→~16ns), verify-mode dep reuse (`tracking.ts:runVerify` — steady-state effect/computed re-runs verify the previous dep list positionally instead of Set-teardown+rebuild: zero Set ops + zero allocations per re-run; measured 2.0–2.2× effect propagation, 1.85× batch-50, 2.6× 10k-effect re-run, memory-neutral), **array+flag effect queue** (`batch.ts` — the tier-2 effect drain is an ARRAY + intrusive per-effect membership flag `_eq` + pass-generation counter `_vg`, replacing two Sets + a scratch Set; ~8× on the enqueue+drain of 100 effect closures → flipped wide fan-out + batch-50 to Pyreon wins; flags lazily created only when an effect enters the queue so retained heap is neutral), **lazy-computed inline dirty-propagation + fused cascade walk** (`batch.ts`/`computed.ts` — a default (lazy) computed's recompute is dirty-mark-only + idempotent (it delegates to the canonical `_markLazyAndPropagate`), so it propagates INLINE during the write's notify phase like Preact's write-time DFS; `propagateLazyDirty` walks SINGLE-SUBSCRIBER chains (the deep-chain shape) ITERATIVELY over the computed's fields via the `notify._c` back-ref stamped by `_markRecompute` — per hop no closure call, no WeakSet lookup, no depth bookkeeping, zero JS-stack growth at any depth (only fan-out levels recurse, depth-bounded); a pure-computed cascade — diamond, deep chain — never enters the pending queue; eager `{ equals }` computeds still settle in the tier-1 queue before effects), **signal no-subscriber write fast path** (`_set`/`_trigger` skip the inline-batch window entirely when the signal has zero subscribers). The 2026-06 create-path opts (`createSelector` inline-first-subscriber, baked text placeholder) cut the create-10k gap vs Vanilla ~31%.
