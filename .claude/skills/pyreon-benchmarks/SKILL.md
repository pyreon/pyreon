# Pyreon Benchmark Results and Measurement Protocol

> Extracted verbatim from CLAUDE.md. This is the authoritative copy — edit it here.

**Pyreon (idiomatic JSX) leads a synthetic krausest-style row-list benchmark** (Chromium via Playwright), after a 2026-06 objectivity pass — but as of 2026-08 that lead is **narrow rather than uncontested**: [Octane](https://octanejs.dev) joined the suite and is the nearest rival — it ties Pyreon on several ops, takes `clear rows` outright (the one op Pyreon is behind on, by one timer quantum), and loses partial-update / remove / create-10k outright to Pyreon (see "Octane is now the nearest rival" below). Treat "fastest framework" as a claim about *this* suite with a live challenger, not a settled fact. **AUTHORITATIVE RUN: 2026-08-14, `--repeat 5`, load 2.70–9.24 traced throughout, Octane 0.1.37, every competitor on its documented fast path.** Verdicts: **Pyreon outright on 5** (create-1k 8.30ms · partial-update 800µs · swap 900µs · create-10k 87.00ms · append 18.50ms), **tie-leader on 2** (replace 8.30ms = Octane 8.40; remove 6.60ms = Octane 6.70 = Solid 6.60), **behind on 1** (`clear rows` — Octane 100µs vs Pyreon 200µs), and `select row` unrankable (Pyreon/Vanilla/Solid all under the 100µs timer floor). This run SUPERSEDES the 2026-08-04 figures: it is the first with the competitor handicaps removed, and the lead narrowed — every remaining margin is now against Octane, which is a genuine peer rather than a distant rival. That clear-rows quantum is DECOMPOSED, not mysterious — and the decomposition was CORRECTED 2026-08-17 with subtree-attributed Chromium CPU profiles (`examples/benchmark/bench-clearprofile.ts`, load ~3 stamped): per clear-1000 the on-CPU split is roughly HALF DOM remove-all (~30µs under the old parent-swap, ~50µs under the current in-place `replaceChildren`) and HALF reactive teardown (selector `.subscribe` disposers ~13µs + cleanup-closure dispatch ~11µs + bookkeeping ~3µs — the earlier "it is all per-row subscriber teardown" attribution came from a whole-suite profile and over-weighted teardown). The teardown half IS at the floor (`_d1` null-out, single Map delete, all leak-class-B-mandatory) and the epoch-lazy-pruning lever remains declined as a hot-path pessimization (see architecture.md). The DOM half moved for CORRECTNESS, not speed: the old `cloneNode(false)`+`replaceChild` swap REPLACED the parent element (dropping `__ev_*` delegated handlers/refs/listeners — `<ul onClick><For/></ul>` lost its handler on first clear); the in-place `replaceChildren` fix costs ~20µs/1000-rows on-CPU, which is INVISIBLE in the fair bench — same-day interleaved 3-framework `--repeat 5` A/B runs (load ~5) measured clear at 200µs [CI 100–200] in BOTH arms (CI-tied with Octane's 100µs in both runs; whether that renders as tie or loss remains a run-noise band). `remove` stays won-or-tied (#2288's removal fast path); `append` is now **OUTRIGHT Pyreon** — #2669 (contiguous-INSERTION fast path, the #2288 mirror) MERGED 2026-08-04 and flipped it: leader 19.00ms on the 2026-08-05 quiet confirm run (load 2.6 stamped, cleanest run of the campaign), down from the pre-#2669 22.2–23.7ms tie band (~15%), and ALSO outright on a load-25 adverse run the same night (noise biases toward ties, so separation under load is the conservative direction). WHICH ops tie still shuffles with machine noise — under load CIs widen and ties multiply (a load-7 run the same day produced 2-outright/2-losses; the quiet run reversed it) — so treat per-op tie-vs-outright as a **band**, and NEVER update this section from a loaded-machine run (stamp `uptime` into the log). Robust signals (2026-08-14 re-measurement, load 2.7–9.2, EVERY competitor on its own documented fast path): a genuine **2.4× edge over React and 3.1× over Preact at bulk-create (10k)**; **7.3× on React's keyed `swap`**; **4.1× on Vue `append`**. **The old "2.4–3.0× over React/Svelte/Preact" and "3.2–4.1× on Vue/Svelte append" claims were partly OUR OWN HANDICAP and are retracted for Svelte and Vue**: Vue was benchmarked on a deep `ref` and Svelte on deep `$state` — the proxy-per-row path both projects' performance guides tell you NOT to use for a replaced list — and Svelte additionally paid a redundant 10,000-object `.map()` INSIDE the timed region. With `shallowRef` / `$state.raw` and that map removed, Svelte create-10k is **1.19×** (was reported ~2.5×) and Svelte append **1.41×** (was ~3.2×); Vue create-10k is **1.06×**. Vue's append stays genuinely slow (4.1×). Only measurable cost vs **Vanilla** is bulk-create (~6–7%, from per-row signal alloc + cleanup closure + keyed-For map). On **retained memory Pyreon is 3rd of 8 — 2nd among FRAMEWORKS, 0.03MB behind Preact and ahead of Solid, Octane, Svelte, Vue and React** (2026-08-14 authoritative run: Vanilla 2.38 · Preact 2.47 · **Pyreon 2.50** · Solid 2.56 · Octane 2.60 · Svelte 2.66 · Vue 2.69 · React 2.86 — the ordering is unchanged from 2026-08-04 and survived the competitor fast-path corrections, which is what makes it the most durable claim in this file; the absolutes sit ~+0.2MB uniformly above the 2026-07 baseline of 2.26/2.22 — a Chromium/run-baseline shift, not a Pyreon regression, and the Preact gap is 0.04MB in both eras). **This line previously claimed 2.90-2.92MB / mid-pack / "the one dimension it does NOT lead" — that was OUR OWN BENCH SCORING US WRONG.** The retained metric read `usedJSHeapSize` after 3 SYNCHRONOUS `gc()` calls, which never yield: reclamation that completes on a later event-loop turn was still counted, so **garbage awaiting collection was reported as "retained"**. Pyreon read 2.90 and settled at 2.23 once given turns (0.67MB reproducibly, 3/3 runs); Preact/Solid/Svelte/React settle immediately and were unaffected — so the old recipe silently penalised ONLY the framework with deferred reclamation and manufactured a ~32% gap that did not exist. Fixed 2026-07-17 (`bench-fair.ts`: GC + yield until the counter stops moving, hard-capped): Vue also improved 3.98→3.48 and Vanilla 2.62→2.12, which is the evidence the fix is uniform rather than self-serving. **Attribution (heap snapshot, node self-size by type) also REFUTES the old stated cause** — Pyreon's `code` space is 579KB vs Preact's 596KB (we ship LESS code), and the JS-only object graphs are near-identical (1.50 vs 1.46MB); the gap was never bundle/code-space. Honest residual: Pyreon uniquely defers ~0.67MB of reclamation by one event-loop turn (released on the next turn in any real app — a latency, not a leak); worth understanding, not a standing loss. Retained has real cross-run variance (Solid measured 2.27–2.97 across same-day runs) — treat mid-table ranks as a band.

### Octane is now the nearest rival (added 2026-08, 8th framework)

[Octane](https://octanejs.dev) — Dominic Gannaway's compiled React framework, successor to Inferno — is in the suite as of PR #2635, and it is **by a clear margin the closest thing to Pyreon that has been measured here**. It displaces Solid as the nearest competitor on most ops.

Pooled head-to-head, `--repeat 3` (60 samples/op, same page-isolated + forced-GC + adaptive-warmup protocol):

| Benchmark | Vanilla | **Pyreon** | Octane |
| --- | --- | --- | --- |
| Create 1,000 | 10.50 | **10.30** | 10.90 |
| Replace 1,000 | 10.40 | **10.50** | 10.90 |
| Partial update | 1.00 | **900µs** | 1.00 |
| Select row | 0µs | **0µs** | 100µs |
| Swap rows | 1.00 | **1.00** | 1.10 |
| Remove row | 7.80 | **8.10** | 8.20 |
| Clear rows | 200µs | **300µs** | 100µs |
| Create 10,000 | 102.40 | **107.60** | 111.80 |
| Append 1k→10k | 25.40 | **27.20** | 29.40 |

**Verdict: Pyreon 4 outright (create-1k, replace, create-10k, append), 4 CI95-ties (partial update, swap, remove, clear), 1 unrankable (select — Pyreon under the timer floor, Octane at 100µs). Octane takes no op outright.** Retained heap after suite: Pyreon 2.48MB vs Octane 2.56MB.

**The one op where Octane genuinely IS better is `clear rows`** — across the three 2026-08-04 full-field runs its median is 100µs vs Pyreon's 200µs (one timer quantum), outright in 2 of 3 runs. This gap has been INVESTIGATED AND ACCEPTED, not left open: the quantum is the per-row subscriber teardown (2 mandatory disposals per row — the app-owned label signal + the selector-driven class effect; skipping them is a Class-B leak), the disposal chain is already at its floor, and the only further lever (epoch/lazy pruning) would add a per-notify branch to the hot path — a bad trade. If Octane clears cheaper, it is because its architecture carries less per-row subscription state, which is the same trade that loses it partial-update to Pyreon's fine-grained bindings. (2026-08-17 refinement: the "all teardown" half of this attribution was corrected — DOM remove-all and teardown are roughly EQUAL halves of the op; see the corrected decomposition in the header paragraph and in `references/core-micro-benchmarks.md`. The accepted verdict stands: neither half has an honest lever left.)

Scope caveat SUPERSEDED (2026-08-04): the full 8-framework field now has three same-day `--repeat 5`-class runs, the authoritative one at 100 pooled samples/op under sustained load ~4 (load-stamped). Its verdicts: Pyreon outright on partial-update, remove, create-10k; best-framework-median CI-ties on create-1k, replace, swap, append (Pyreon 1.00× in the vs-best table on all four, tie partners Octane and/or Solid); select at the timer floor; clear outright Octane. The 7-framework table above predates Octane and is kept as the historical per-op medians record — the 8-field band in the header paragraph is the current ranking claim.

**Coverage is the bigger gap.** Octane's own suite runs 15 scenarios; ours meaningfully covers ~5 of them (js-framework ops, bundle size, SSR throughput, hydration, a Pyreon-vs-React TodoMVC). We have **no** cross-framework coverage for: streaming SSR, portals, deep context propagation, effect-heavy lists, memoization walls, async waterfalls, or dbmon-style sustained updates. "Fastest" claims from this suite are scoped to keyed row-list DOM work and should not be generalised past it.

### Hydration (cross-framework, 2026-08-17): statistical TIE with Vue in the cleanest run; treat as tie-to-1.05× band

`bench-hydration.ts` (1000-row SSR table → interactive; per-framework fixtures from each framework's OWN server renderer; adoption node-identity + row-count + real-click interactivity gates in-page per iteration; `--repeat 3`, pooled n=60). After the prop-level plan-specialization + row-shape-signature PR (and its two harness-fairness fixes — React's hydrate now `flushSync`-committed instead of awaiting rAF→setTimeout inside the timed region, and the runner AWAITS async verify callbacks): cleanest quiet run (load 8.2 stamped, decaying) **Pyreon 6.70ms [6.60–6.80] 🥇-nominal, Vue 6.75ms [6.60–6.90] 🤝 CI-overlap tie**, React 8.15ms (1.22×), Preact 9.50ms (1.42×); a same-day loaded run posted Vue ahead by 0.20ms (1.03×). Same-protocol baseline-runtime control runs the same day: Vue ahead by 0.30ms (1.04–1.05×, non-overlapping CIs) twice, tie once — so the PR closed a real ~0.1–0.3ms gap into the noise floor, and the honest claim is a **tie-to-1.05× band, NOT a win** (between-run drift is ±0.1–0.15ms at these magnitudes; #2694's earlier 1.20× was that session's conditions — its React 1.44× control included the rAF harness artifact now removed). The timed region is floor-dominated: ~1.4ms/iter is Pyreon hydration JS (profiled: compiled-adoption spot-verify + bind + For-block parse), the rest is the forced layout of the 1000-row table + GC that every framework pays — which compresses ratios; compare absolute gaps, not ratios, when working on this bench. Residual Pyreon pays and Vue does not: per-row `$`-marker normalization + spot verify (~0.2–0.4ms/1000 rows), bought by the `k:`/`$` marker architecture that funds keyed adoption + strict verify-then-bind. Solid/Svelte/Octane are ABSENT (their hydration needs their real compiler toolchains wired in — follow-up). Reproduce: `cd examples/benchmark && bun bench-hydration.ts --repeat 3` (quiet machine, load-stamped).

**ONE honest Pyreon entry** = the idiomatic JSX users ship (`pyreon.tsx`). There is no manufactured "compiled" tier — the compiler already lowers idiomatic JSX to the same `_tpl()` cloneNode + fine-grained-binding output a hand-written `_tpl()` would (PR #1501 removed a per-row `_bind()` inefficiency for static `<For>`-item reads, making them byte-identical). Earlier "4–8× on small ops" claims were a harness artifact (an `rAF` commit wait inside the timed region + missing per-run resets), fixed by tightest-commit timing (`flushSync`/microtask/synchronous per framework) + per-run reset hooks.

**Methodology** (designed for objectivity): per-framework page isolation (`page.goto('?framework=X')`); forced GC between iterations (`--expose-gc`); adaptive warmup; 20 timed runs + median + 95% bootstrap CI + CV + CI95-overlap `🤝` tied-marker; real Chromium on production `vite build`; DOM verification per iteration; seeded RNG; real published deps; tightest-commit-per-framework (no `rAF`); per-run resets on every op; randomized + per-pass-reshuffled execution order; machine stamp printed; retained-heap metric (`--enable-precise-memory-info`, post-GC). **Honest limits**: this is CPU-objective, not real-world-async-latency (React's default path would be higher); the deepest limit is **author-judge** (the framework author writes + judges the bench) — only an upstream submission to the independent krausest/js-framework-benchmark fully resolves it (a ready-to-submit `frameworks/keyed/pyreon` implementation is staged at `contrib/krausest/pyreon-keyed/` — built + 8-op-smoked against PUBLISHED npm packages; submission steps in its README-SUBMISSION.md — the upstream PR itself is a human decision). A **real-app head-to-head does not exist yet** (the `cpa-pw-app-*` ports run on Pyreon compat shims, not the real frameworks) — "fastest" claims stop at this synthetic suite's evidence.
