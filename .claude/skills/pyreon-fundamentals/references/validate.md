# @pyreon/validate

- **@pyreon/validate**:
  - Pyreon's `s` validator runtime + DX helpers on Standard Schema. `withField`/`getMeta`/`resolveMetaField`/`parseReactive`/`watchValid`/`formatErrors` (`parseReactiveAsync` supersedes stale in-flight results — an awaited stale frame resolves to the LATEST run's verdict). `s` runtime: primitives + object/array composition + modifiers + 20+ checks + object algebra (`.pick/.omit/.partial/.required/.extend/.merge/.keyof/.catchall`). ASYNC members (`.refine`/`.transform`/registered `.serverCheck`) work inside EVERY composition (union/DU/intersection/map/set/record/tuple + the JIT — a sync `parse()` of an async tree reports the ONE canonical "use parseAsync" issue at the root). `s.discriminatedUnion` accepts literal/enum/nativeEnum discriminants (dev-guarded: non-registrable field or duplicate tag throws at construction). **`.catch` runs against a PRIVATE child ctx** — a catch window can never eat a SIBLING field's issues (fuzz-found shared-ctx bug, both backends). `toJsonSchema(schema)` (subpath `@pyreon/validate/json-schema`) emits draft 2020-12 (input-shape contract; unrepresentable kinds throw or `{ unrepresentable: 'any' }`; cyclic lazy throws — no $defs in v1).
  - **Tree-shaking**: DX helpers tree-shake clean; the chainable `s.` API does NOT (prototype methods) — use `pyreon({ optimizeValidators: true })` to rewrite module-level `const X = s.<chain>` to the lean `@pyreon/validate/mini` form at build time (function chaining in, tree-shakeable output, parity-locked; ~−41% measured). `pyreon({ compileValidators: true })` inlines a monomorphic verdict for `.is()` (1.6–3.0× faster, nanoseconds — only matters in hot `.is()` loops). Both flags cover statically-analyzable chains within the emit slice (primitives + common checks + object/array/optional); out-of-slice chains gracefully stay full-runtime.
  - **Perf standings — RE-MEASURED 2026-08-31 on a SETTLED machine (1-min load 5.18, but 5/15-min averages 13.9/62.5 — quieter than the earlier runs, NOT an idle box; the results file records this in its first line) against zod 4.5.4 / valibot 1.4.2 / arktype 2.2.3 / typebox 0.34.52 / typia 14.0.4 / yup 1.7.1 / joi 18.2.5. NOTE contention INFLATES every absolute and widens CIs into 🤝 ties, so a loaded run reads as MORE dominant than reality — an earlier loaded run of this same code showed 'fastest-or-tied 10/12' on cells the quiet run splits. The headline changed: Zod 4.5 shipped `z.compile()` (a `new Function` codegen path) and a ~7.5×-faster failure path, so the old "fastest-or-CI-tied on all 12 cells; never behind" claim is FALSE and must not be restated.** The bench (`bench/validation.ts`) now runs TWO axes — `parse` (produce an output value) and `check` (boolean verdict) — over 7 COMPETITOR libraries in 8 competitor entries (zod twice: interpreted + compiled), plus pyreon itself and a `pyreon-legacy-is` control = 10 entries total. TypeBox runs `check` only (no output-producing equivalent); Zod has no boolean-only API so its `check` cells are a full `safeParse` (both disclosed in the printed footer).
    - **`check` axis: fastest or 🤝 CI-tied on 10 of 12 cells** — outright wins on FLAT OBJECT (31ns, ahead of ArkType 35 / TypeBox 39), array-of-20 (51ns), deep-nested (10ns) and object-with-array-of-objects (46ns); tied for first with TypeBox/typia/ArkType/zod-compiled on number-range (both paths), flat-object invalid, deep-nested invalid, and DU (both paths). Both losses are `string.email` (ArkType + typia ~1.3× ahead).
    - **`parse` invalid: outright win on FOUR of five shapes** — 1.1–3.4× Valibot, 7.3–10.9× Zod (interpreted AND compiled), 12.4–37.8× ArkType, 1.6–6.1× typia, 19–135× Joi/Yup. The fifth (scalar number-range invalid) goes to typia by 1.2× (42 vs 49ns).
    - **`parse` valid: we are NOT ahead anywhere on this path.** zod-compiled wins scalar number-range (2.8 vs 5.0ns), array-of-20 (108 vs 116ns) and object-array-of-objects (117 vs 134ns) — these four cells RE-MEASURED 2026-09-06 after #3316 (parse seam inlinable: `S.parse` scalar 10.2 → 4.8ns; `bench/results/final-2026-09-06-four-cells.txt`; the du cell reads 8.67 vs 8.69, a tie as before; everything else on this line is still the 2026-08-31 run); ArkType+typia win scalar-email (26/27 vs 33ns); ArkType wins flat object (36 vs 49ns); deep-nested and DU are 🤝 CI-ties with zod-compiled. Still ahead of interpreted Zod / Valibot / Yup / Joi on every valid shape. Ahead of interpreted Zod / Valibot / Yup / Joi on every valid shape. Residual causes: ArkType ALIASES the input (no clone) while Pyreon returns a stripped clone (deliberate semantic), and Pyreon's `Result` envelope is built by the `parse()` seam AROUND the generated function. The seam was the first lever and is DONE (#3316 — the hot seam's SIZE decided inlining: a tiny `parse()` method inlines, the old 10-line one did not; the envelope allocation itself is ~0.4ns and is NOT the cost). **Second seam lever, 2026-09-07: a pure tree installs `parse` as an OWN property (a closure over `_compiled` + `_pureCtx`, built in the same pass and deleted on invalidation) — `number.int.range` 5.02 → 4.63ns on the process-isolated four-cell runner (two runs; `bench/results/own-parse-2026-09-07-four-cells.txt`), deep cells unchanged. The in-process probe that sized #3316 has a ±1.5ns ARM-SLOT bias (the same function reads 4.48 in slot 2 and 2.99 in the last slot; the first slot is always penalized), so the recorded `seam = 2.21ns` magnitude is inflated; sub-ns seam verdicts come from `bench/four-cells.ts` only.** On the scalar cell the emitted validator alone ties zod-compiled's whole call (2.62 vs 2.62ns); the residual 2.2ns is the envelope + pure-ctx call. On the deep cells (array-of-20, object-array-of-objects) the residual was ATTRIBUTED to the per-item stripped CLONE, on the premise that zod-compiled returns the input by reference — that premise is FALSE (its emitted parser builds `{ k: v… }` per object and `new Array(n)` per array; `Z.parse(clean) === clean` is false), so clone-on-demand was never a lever against it. What did differ per array was our `ctx.path` materialisation (`P = mutablePath(ctx); P.push("items"); … P.pop()`) on every parse, now skipped for pure-inline element subtrees (pending indices reach failure sites as trailing arguments; a fallback still flushes), plus pure composite fields absorbed into the object literal — worth a nominal 5–13% on the object cell and nothing on the 20-item array in two quiet-box raw-emit runs (CI-overlap). The remaining gap on those cells has NO named mechanism; note the in-process harness ranks zod-c SLOWER than us on array-of-20 (150 vs 120 ns), so the bench's pool + process isolation are part of the standing.
  - **`.is()` has its OWN verdict-only JIT (2026-08)** — `tryCompileJitCheck`, a second emission from the same codegen: every failure site is a bare `return false`, the root returns `true`, no output value is constructed, no issue is allocated, and the emitted function takes ONLY the input (no ctx). Before this, `.is()` ran the PARSE validator and threw away both the issues and the strip-clone, which cost 5–33× vs TypeBox's `Check()` on invalid input. Measured as an in-run interleaved control: **1.2×–25.7×** (flat-object invalid 180→7ns, deep-nested invalid 137→7ns, DU invalid 85→7ns, array-of-20 valid 119→51ns). Shapes it cannot express — a `_runInto` fallback, or a check with neither an inline condition nor a `_pred` predicate (both need a real ctx to decide) — are REFUSED and `.is()` keeps the previous path. Locked by `jit-check-differential.test.ts` (contract: `is(x) === parse(x).ok`), which asserts PER-BLOCK how many schemas the verdict emitter actually served plus a fuzz coverage floor — otherwise a refusal makes the suite compare `parse` to itself and pass vacuously. Bisect-verified in five directions.
  - **Two measurement bugs were found and fixed in the harness itself; both invalidate any number taken before 2026-08-31.** (1) With one CONSTANT input per scenario the call is loop-invariant and V8 hoists it out of the timed loop — ArkType's `string.email` read ~3ns/op (below its own regex cost) while un-hoistable libraries reported their real ~28ns, i.e. the table ranked INLINABILITY. A result sink does NOT fix it; only rotating an input POOL does (now 8 same-shape different-value entries per scenario). (2) Running one library's 3 processes consecutively let a load burst land entirely on that library (a Pyreon cell read 155ns against its own 5ns) — processes are now ROUND-ROBINED across the libraries in a row, so contention widens every CI together and reads as a 🤝 tie. Also: the old "setup cost" table measured shared scenario construction (all nine columns ~1.4ms); it now reports only the explicit compile CALL (`z.compile` 17–67µs, `TypeCompiler.Compile` 11–50µs across the seven scenarios) and `—` for libraries that compile lazily or at definition time.
  - **`.is()`'s verdict function is built in the SAME pass as `_compiled`, NOT lazily** — and that is a CORRECTNESS constraint, not a style choice. A chained method mutates a schema in place and invalidates only the schema it was called on, never its ancestors; that staleness is benign while one compiled artifact serves every reader (they are stale TOGETHER), but two artifacts built at different moments go stale DIFFERENTLY and `.is()` starts disagreeing with `.parse().ok` (repro: a shared leaf extended after a parent has been used). Invalidating both is NOT sufficient — a verdict compiled later reads a newer tree than a stale parse validator. `.is()` still reads ONE field on the hot path (routing it through `_getCompiled()` per call cost 7ns vs 5ns and lost the scalar CI-ties). Locked by the shared-child specs in `jit-check-differential.test.ts`, bisect-verified both directions.
  - **typia is AHEAD-OF-TIME and cannot be built at runtime** — its validators are generated from a TypeScript TYPE via `ttsc` + TypeScript 7, a toolchain this repo pins away from (TS7 removed the classic Compiler API). Its bench fixtures are therefore compiled OUTSIDE the repo and the emitted plain JS is vendored at `bench/typia/`; nothing gates that file's freshness except the bench's own cross-library correctness gate, which fails if it drifts. Use `plain.createValidateClone` on the parse axis — `typia.validate` returns the input BY REFERENCE and `typia.is` skips both the allocation and the error collection, so either would credit typia for work it never does.
  - JIT architecture (unchanged, still the parse-path foundation): `tryCompileJit` recursively flattens pure object/array/primitive/DU shapes to one monomorphic `new Function` with static-path elision (`ctx.path` untouched on the valid path; issue paths reconstructed only at failure sites), async-aware fallback deferral, a memoized format resolver + `_pred` predicates so a format check costs one predicate call on the valid path, a lazy `EMPTY_PATH` sentinel (a scalar/flat-object parse allocates ZERO path arrays), a sync-only body when nothing can defer, DU-root compilation to a raw-value discriminant `switch` with member bodies inlined, and all-inline-primitive object bodies constructing their strip-clone as ONE object literal. A fully-inline tree is branded `_jitPure` and the public seams (`parse`/`~standard.validate`) reuse a per-schema ctx.
  - Locked by the JIT↔interpreter differential fuzz (now FIVE suites — incl. the verdict-JIT `is() ≡ parse().ok` suite — the DU suite covers NaN/enum/`__proto__`/fallback/async members + nested DUs) + `format-registry-routing` (the memoized resolver still swaps to the `/server` validator on install).
