# @pyreon/table

- **@pyreon/table**: TanStack Table adapter — `useTable(() => opts)` returns `Computed<Table<T>>` (call `table()`; options-as-FUNCTION so signal reads auto-track). `flexRender` for column-def templates; **`flexRenderCell(table, rowId, columnId)`** is the fine-grained per-cell primitive — inside a keyed `<For>`, plain `flexRender(cell…, cell.getContext())` FREEZES on an in-place value change (the reconciler reuses the cell + never re-runs its body), so read cells via `<td>{() => flexRenderCell(table, row.id, cell.column.id)}</td>` passing the ACCESSOR (`table`, not `table()`). The adapter keeps ONE coarse version signal (drives the `<For>` structure) PLUS **per-row version signals** — a cell passed the accessor subscribes to only its row, so an in-place data edit re-runs just the changed rows' cells (state changes = sort/filter/selection/visibility bump all rows, coarse+correct for state-reading cells; distinguished from the spurious TanStack auto-reset onStateChange via a VALUE compare `sameTableState`, not reference). **Bench** (`bench:table` counts + `bench:table:wall`, both vs `@tanstack/react-table` wrapping the SAME table-core@8.21.3): single-cell edit re-runs **6 cell units** (only the changed row) = idiomatic memoized react-table (6) but with ZERO `React.memo` boilerplate and N-independent; wall-clock **7-9× faster than naive react-table, ~1.1-1.2× faster than hand-memoized** (N=100/1000). The wall bench's Pyreon fixture compiles through the REAL `transformJSX` (`pyr-tpl` — what vite-plugin apps ship, the verdict baseline; the hand-`h()` path stays as a transparency column) and every cell carries an untimed real-DOM correctness gate. Honest losses (disclosed, fine-grained mount tax + coarse-on-state): mount ~2× / replace ~1.1-1.3× (per-cell reactive-binding setup — MEASURED as the true cause: the compiled fixture closes only ~10% of the mount gap, so it's the price of the per-cell subscriptions buying the update wins, NOT an h() harness handicap as previously attributed), sort ~2× vs memo-row (coarse re-runs all cells; react-memo does 0 but needs the user's memo comparator; vs NAIVE react, sort is 🤝 tied). Sibling verdict in `@pyreon/virtual`'s bench (same treatment): steady-state scroll **1.3× faster** than react-virtual on the compiled path, fixed-size mount 1.1× slower (one-time ~16µs on a 10k list — same binding-setup class), `item()` dynamic mount 1.3× the fixed mount (per-row signal tax, amortized by the scroll/remeasure wins). **Known limitation** (pre-existing base-adapter, affects plain `flexRender` too): a data edit that changes the SORT ORDER updates cell VALUES but doesn't re-position the keyed rows until the next structure/state change — `getSortedRowModel`+`<For>`+version-bump timing; `toggleSorting`/`setSorting` reorder normally. `.map()` over rows is the anti-pattern (full `<tbody>` rebuild). Re-exports all table-core; `public-surface.test.ts` snapshot locks the export set.
