# @pyreon/query

- TanStack Query adapter: `useQuery`, `useMutation`, `useInfiniteQuery`, `useQueries`, `useSuspenseQuery` and the rest; `/persist` and `/devtools` subpaths.
- Pass `useQuery` options as a function (`useQuery(() => ({ queryKey: [id()], … }))`) so `queryKey` can read signals and refetch reactively. `useMutation` takes a plain object.
- Persisted mutations (`/persist`, `persist-mutations.ts`). TanStack persists a mutation only while paused, so one in flight is lost when the tab dies (#4723). The four `persistQueryClient*` functions (TanStack's signatures) and the provider apply one contract:
  - Which: `shouldPersistMutation(mutation, client)`. Pending, not `meta: { persist: false }`, storable (variables survive JSON strictly; context and meta only need to be writable; a `mutationKey` cannot hold a cycle or BigInt since TanStack hashes it). Then PAUSED (TanStack parity: never persist less than TanStack) or IN FLIGHT and resumable: the key resolves to a registered `mutationFn` (the function a restored copy runs; an inline override does not matter), or keyless and running the client default. A keyed mutation left out gets a dev warning. The storability check is cached per mutation (TanStack dehydrates on every cache event). A `failureReason` that cannot be written becomes `{ name, message }`, so a retry never loses the whole write.
  - Precedence is TanStack's: explicit option, then the client's `defaultOptions.dehydrate`, then this default.
  - Ownership: a Web Lock per persisted mutation (held until it settles) and an owner lock per page, taken with the first mutation lock and released once the page owns nothing (a held Web Lock blocks the back/forward cache). A restoring page leaves a mutation whose lock is held, writes it back unchanged, and on release re-reads the entry's CURRENT owner from storage (a takeover re-tags it) and takes it over only if that owner is gone. A restore TanStack discards (expired, busted) releases what it adopted. Without Web Locks an in-flight mutation is not persisted. Entries are tagged with their lock by the `state` object `dehydrate` copies by reference.
  - Writes: an immediate write (coalesced per microtask) when a mutation becomes owned and when it settles, the latter before its lock is released; a page that is not subscribed only edits its own stored entries. After `pagehide` the page is frozen (no writes until `pageshow`): teardown aborts fetches and the dying page would otherwise settle them as errors and write them out of storage (found in real Chromium on reload).
  - Delivery is at-least-once. Tests: `persist-mutations.test.tsx` (a fake shared LockManager simulates tabs and tab death) and the two-tab cases in `e2e/pwa-offline.spec.ts`.
- `defineQueries({ … })` declares named parallel queries.
- Results are fine-grained per-field signals, created lazily behind property getters.
- Type helpers `QueryData`/`QueryError` unwrap the result bags.
- Re-exports query-core, pinned repo-wide through `overrides`.
- Native: `PyreonQueryCache` (Swift + Kotlin) is the query client. Keys are the colon-joined web keys (`['todo', 5]` → `todo:5`), and a query is LIVE once `run` registered its request. The live registry is a leak surface: Swift holds weak refs and unregisters in `deinit`; Kotlin removes by identity in `RememberObserver.onForgotten` / `onAbandoned`, which works only because the emit `remember`s the `PyreonQuery` itself. `invalidateQueries` marks entries stale (kept and served) rather than dropping them. Both rules have cleanup tests in `native/tests`.
