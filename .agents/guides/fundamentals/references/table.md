# @pyreon/table

- **@pyreon/table**: TanStack Table **v9** adapter — `useTable(() => opts)` returns the **`Table` INSTANCE directly** (no `Computed`, no `table()` call; options-as-FUNCTION so signal reads auto-track). The v8 accessor wrapper + version counter are GONE: v9 exposes a pluggable reactivity seam (`coreReactivityFeature`) and `pyreonReactivity()` backs its atoms with Pyreon signals, so `table.getRowModel()` read in any reactive scope subscribes natively. **v9 requires EXPLICIT feature registration** — build a `tableFeatures({...})` object ONCE at module scope (it is a compile-time type param) with only what you use; the core row model is automatic, the rest are slots: `rowSortingFeature`+`sortedRowModel: createSortedRowModel()`, `columnFilteringFeature`+`filteredRowModel`, `rowPaginationFeature`+`paginatedRowModel: createPaginatedRowModel()`, `columnVisibilityFeature` (**required for `row.getVisibleCells()`**), `rowSelectionFeature`, `globalFilteringFeature` (needs columnFiltering). `stockFeatures` = all 16 features but NOT the row models. Core types take a leading `TFeatures`: `ColumnDef<typeof features, T>`, `Table<TFeatures, T>`. `table.getState()` and top-level `onStateChange` are REMOVED → `table.store.state` / `table.atoms.<slice>` and per-slice `on<Slice>Change` (**supplying one puts that slice in CONTROLLED mode** — core stops self-updating it). Pinning is logical (`start`/`end`, not `left`/`right`); `sortingFn`→`sortFn`; `columnSizingInfo`→`columnResizing`; `getIsSomeRowsSelected()` now means "at least one" INCLUDING all. `flexRender` for column-def templates; **`flexRenderCell(table, rowId, columnId)`** is the fine-grained per-cell primitive — inside a keyed `<For>`, plain `flexRender(cell…, cell.getContext())` FREEZES on an in-place value change (the reconciler reuses the cell + never re-runs its body), so read cells via `<td>{() => flexRenderCell(table, row.id, cell.column.id)}</td>`. The adapter keeps **per-row version signals**: a cell subscribes to only its row, and the whole cell LOOKUP runs untracked (every v9 step — `getRowModel`/`getVisibleCells`/`getContext` — is a derived-atom read, so leaving any tracked re-subscribes the cell to table-wide state and coarse-invalidates everything). **The inner cells LOOP needs the same discipline — drive it with `visibleCells(table, row.id)`, never the captured `row.getVisibleCells()`**: the tracked form's memo deps read `table.options` (changed by EVERY options sync, data edits included), so a single-cell edit re-ran ALL N cells-list accessors (measured 1000-of-1 at N=1000, ~3× a memoized react-table's wall-clock); `visibleCells` subscribes to the row signal + the column-geometry slices (visibility/order/pinning/grouping) and looks cells up UNTRACKED from the CURRENT model (bridge-less tables fall back tracked/coarse). Companion fix that makes those slice subscriptions quiet: the atom bindings default `compare` to `Object.is` (TanStack Store reference parity — core creates its per-slice `table.atoms[key]` with NO compare while their fn reads `table.options`, and Pyreon's bare `computed` notifies unconditionally, so every data edit used to re-notify every slice subscriber with an unchanged value). Structure/columns changes bump all rows (correct-by-over-invalidation); columns are compared by STRUCTURAL SIGNATURE (now incl. `groupedColumnMode` — it changes the leaf-column list without touching `columns` or row ids), not array identity, because an inline `columns: [...]` literal churns its reference every sync. **Bench** (`bench:table` counts + `bench:table:wall`, both vs `@tanstack/react-table` wrapping the SAME table-core@9.0.0): single-cell edit re-runs **6 cell units / 1 DOM write** (only the changed row) = idiomatic memoized react-table (6) but with ZERO `React.memo` boilerplate and N-independent (verified at N=100 AND N=1000 on v9). Wall-clock RE-BASELINED on v9 (2026-08-17, two runs, load 3.8/7.0 stamped, post `visibleCells` + Object.is-parity): **update-1cell ~1.3× FASTER than hand-memoized react-table at BOTH N (10-25× vs naive)** — before the fix it was 3.0× SLOWER at N=1000 (the tracked inner-loop O(N) overhead). Honest losses, re-confirmed on v9: **mount ~1.7-1.9×** (the price of allocating N×M fine-grained bindings + N keyed reconcilers up front; also carries a core-runtime 2×-accessor-invocation-at-mount inefficiency — follow-up, runtime-dom scope); **replace ~1.1-1.3× / partial CI-ties** (mount cost again); **on a SORT the keyed path re-runs all cells (600/6000 units, wall ~1.8-2.2× vs memo-row) where react-memo-row does 0** — coarse-but-correct, deliberate + test-locked (a state-reading cell under `React.memo` on `original` silently freezes; ours stays correct), the price of not requiring a user memo comparator. **Known limitation** (pre-existing, affects plain `flexRender` too): a data edit that changes the SORT ORDER updates cell VALUES but doesn't re-position keyed rows until the next structure/state change; `toggleSorting`/`setSorting` reorder normally. `.map()` over rows is the anti-pattern (full `<tbody>` rebuild). The runtime re-export list is now EXPLICIT/curated (not `export *`) so an upstream major is our migration rather than users'; `public-surface.test.ts` snapshot locks it.
