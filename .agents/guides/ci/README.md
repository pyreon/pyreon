# CI architecture

Read before adding or changing a workflow, job, required check, or cache key.

## Constraint: runner slots, not minutes

- The org is on GitHub's free plan: 20 concurrent jobs org-wide, 5 of them macOS, shared by every open PR. Runner minutes are unmetered on a public repo.
- PR wall-clock is dominated by queue wait. The levers are job count and DAG depth, not per-job speed.
- A cell's fixed setup (queue + checkout + `setup-pyreon`, plus Playwright for e2e) is about a minute. Splitting work into more jobs only helps while runners are idle.

## Design rules

- A gate that takes seconds is a step, not a job. A new job needs a written reason it cannot be a step.
- Keep the graph shallow: Install, then Fast Gates, then expensive fan-out
  (plus the one aggregator). The extra preflight edge is intentional: it keeps
  expensive runners idle until cheap deterministic checks prove the commit is
  worth testing.
- Every gate step inside `Fast Gates` / `Build` runs with `if: ${{ !cancelled() }}`, so one push reports every red gate.
- Job-level preflight and aggregate verdicts must also respect cancellation.
  `Test` uses `!cancelled()` so failed prerequisites still produce a verdict,
  while superseded PR runs release their concurrency slot. An `always()` job
  can survive ordinary cancellation and leave the newest run pending.
- Bootstrap build deadlines must settle the runtime, not just the build promise.
  The shared bounded-process helper stops owned POSIX descendants and destroys
  inherited pipes. Bootstrap allows 250ms output drainage after parent exit;
  incomplete drainage fails closed. Windows cleanup targets the direct child.
- Matrices and decide outputs are fail-closed. A detection error runs the full set, because a skipped required check reports success to branch protection.
- Generated-output freshness must reject failed Git comparisons and include
  new unstaged files within the generator-owned paths. Empty stdout alone
  does not prove freshness; unrelated working-tree edits remain outside the check.
- Generated troubleshooting navigation lists categories without persisting entry
  totals. Independent catalog additions must merge into a fresh index without
  conflicts over derived counters; category pages retain every entry and fix.
- Expensive matrices use `fail-fast: true`, and sequential batches stop on the
  first real failure. Preserve diagnostics/upload/cache steps with
  `if: always()` rather than continuing expensive test work after red.
- Two deciders that gate the same downstream job must classify every path identically (`scripts/affected.ts` vs the e2e decide; `scripts/native-surface-touched.ts` feeds both native decides).
- Never rename a required job. To retire one, drop its name from both protection authorities before deleting the job. Never add a required name casually: it hangs every open PR on "Expected" until that PR's next push.
- One artifact ⇒ one cache key prefix ⇒ one writer. Duplicate writers fill the 10 GB actions cache and evict the small entries every PR needs.
- Small content-addressed stores (the native compile-verdict store) are saved from every run, because main's push runs are frequently cancelled.
- When adding a matrix cell, ask whether it needs its own runner or just its own step. Default: a step. Select cache ownership by membership and key the cache by its stable category, never by a batch name that changes with packing. `native-rest` has exactly one cache writer even when it shares a runner.
- All PR selectors in `ci.yml` use `CI_BASE`, the event's immutable base SHA. Do not fetch a moving base independently in each cell: selection and execution must use the same diff while main advances.

## `ci.yml` jobs

| Level | Job | Contents |
| --- | --- | --- |
| 1 | `Install` | install → decide → build `lib/`. Outputs `code`, `affected`, and the batched `typecheck-` / `test-` / `e2e-` / `scaffold-matrix` lists. |
| 2 | `Fast Gates` | Every lib-free gate: lint, ratchets, docs sync, manifests, export entries, release readiness, doc examples, dependency audit, secrets scan, PR-targets-main. Cheap gates collect all diagnostics. |
| 3 | `Build` | Every lib-needing gate: examples build, verify-modes, bundle + import budgets, distribution, bin liveness, coverage floor + changed packages, the Rust-binary equivalence run. |
| 3 | `typecheck (…)`, `test (…)`, `e2e (…)`, `Scaffold Smoke (…)` | Dynamic cells, packed by `scripts/ci-batch.ts` (LPT by measured weight). Sibling cells cancel after the first failure. |
| 3 | `Test (browser)`, `Release Build`, `bootstrap-exit-codes` | |
| aggregate | `Test` | The single fail-closed aggregator over Install, Fast Gates, and all four matrices (`scripts/ci-aggregate.ts`). It depends on every member so it consumes a runner only for the final verdict. |

- Lib-free vs lib-needing: typecheck, lint and vitest resolve `@pyreon/*` to `src` through the `bun` condition and do not need `lib/`. Exceptions are tests that assert on `lib/` bytes or boot a nested Vite SSR build. A new lib-needing gate goes in `Build`; a lib-free one in `Fast Gates`.
- The local pre-push hook runs only the changed packages' tests, under a time cap (see `.agents/rules/workflow.md`, "Pre-push hook"), so these cells are the ONLY place the reverse-dependency closure is tested before merge. Anything the hook drops must stay covered here or in a required native job.
- `scripts/affected.ts` computes the per-PR package filter. Root configuration, `.github/workflows/ci.yml` and shared-action changes escalate to `--filter=*`. **A changed file never selects zero cells unless it is prose** (Markdown, `.agents/**`, `.changeset/**`, `llms*.txt`, `LICENSE`, `.gitignore`): a repository-level file that no workspace owns (a ratchet baseline at the root, a lint config, a hook, an editor's MCP config, `perf-results/**`) selects `@pyreon/test-utils` as a leaf when one of its tests names the file, or names a script that names it or its top-level directory (`scripts/repo-file-readers.ts`, the same scan the pre-push hook targets tests with); when nobody names it, it selects `--filter=*`. Before 2026-11-17 such a file selected nothing: #4520 changed `readable-oxlint-baseline.json`, every `test (…)` cell was skipped, `Test` passed, and the test that reads the file first ran on the default branch. Any OTHER workflow file is a leaf seed for `@pyreon/test-utils` (its tests lint the workflows), so editing `native-device.yml` no longer reruns every package; it still keeps `affected` non-empty, which the E2E aggregator's decide-says-run invariant depends on. E2E and scaffold selectors also cover shared actions.
- `scripts/ci-batch.ts` uses separate `typecheck`, `test`, `e2e`, and `scaffold` profiles. A suite name is not a global cost: `core` E2E and core package tests are different workloads. The profile records measurement provenance. Unknown members still run with a default weight. Small selected workloads use fewer runners; caps remain 3 typecheck, 3 test, 4 E2E, and 3 scaffold batches. The seven build-only scaffold cells fit on one runner (~49s of measured work after removing repeated root bootstrap); the four `cpa-smoke-app-<x>-compat` cells also run the compat runtime suite (`e2e/cpa-app-compat.spec.ts`) in Chromium against the fresh scaffold's dev server, and the batch that carries one installs Chromium. The cap leaves room for growth.
- `Test` validates `toJSON(needs)` after its dependencies finish. Install and Fast Gates must succeed; each selected matrix must succeed; only explicitly unselected matrices may skip. Missing, malformed, or contradictory selection outputs fail. Healthy runs make no jobs-API calls. Failed runs request job links once, with a ten-second total deadline; unavailable or stale API data cannot change the failed verdict.
- `scripts/check-ci-fail-fast.ts` statically prevents an expensive job from
  bypassing Fast Gates or a matrix from disabling cancellation.
- `ci-main.yml` runs `Coverage (Full)` and `Coverage (Native)` on push to main. Coverage-infrastructure PRs also run `Coverage (Full)`; native coverage runs on main only. Neither is required, so neither runs in the merge queue.
  Superseded coverage PR runs cancel by PR ref; main runs finish
  and coalesce pending work. The static CI policy gate guards both behaviors.

- Native capability disk caches accept only successful probes. A timeout or signal is a transient failure, never evidence that a compiler or module is absent. Failed legacy probe entries are ignored; interrupted module validation fails and retries on the next call. Required Observation validation fails instead of reporting a successful skip. Genuine SwiftUI absence on non-Apple hosts remains an SDK skip.

## Other workflows

- `pr-gates.yml` — `Changeset` and `Diagnose Catalog`. These are label-sensitive (`skip-changeset`, `skip-diagnose-catalog`), so they live apart from `ci.yml`, whose `pull_request` trigger excludes `labeled` (a label would cancel the in-flight run).
- `native-validate.yml` — `Validate emitted Swift + Kotlin`, `Validate emitted Swift (real-SDK typecheck, macOS)`. Both run when the native path classifier OR the native-compiler dependency graph (`affected.ts --category=native/compiler`) selects them; the device lanes use the path classifier alone.
- `native-device.yml` — `iOS — xcodebuild (Simulator SDK)`, `Android — gradlew assembleDebug`. After the path classifier, a `Native inputs fingerprint` job (PR only, `continue-on-error`) builds every gated app's emit at head and base and keeps only apps whose fingerprint moved; an empty output (failure, timeout) falls back to the classifier. Input contract and tests: `scripts/native-inputs-fingerprint.ts`, `native-inputs-fingerprint.test.ts`. Triggers on `opened`/`synchronize`/`reopened`, not `labeled`: a label event re-ran the whole device build on the same SHA (19 times in two days, 1,086 macOS runner-minutes). The `native-device` label is read on the next push; `gh workflow run native-device.yml --ref <branch>` proves the current commit at once.
- `native-device-nightly-status.yml` (`workflow_run` after `Native Device Build`) — keeps the `[native-device] Nightly device build is RED` sticky issue in step with the scheduled run. It was a job inside `native-device.yml` and put a skipped or cancelled row on every PR.
- `size-ceiling-status.yml` (`workflow_run` after `CI`, pushes to `main` only) — keeps the `[size] main is over a size ceiling` sticky issue in step with the four size steps: three in `Build`, and `Check Site Route Budgets` in the e2e cell that ran the `docs` suite. It reads those steps by name; renaming one needs the same change here. The issue closes only when all four have a `success`: a step that did not run is no verdict.
- `main-red-status.yml` (`workflow_run` after every workflow that can run on the default branch) — the alarm for a red default branch; see "Red default branch alarm".
- `bundle-size-diff.yml` (advisory) — does not run on the release PR (`changeset-release/main`); its job-level `if:` skips it.
- `lathe-action-selftest.yml` (advisory) — trigger-level `paths:` filter. A trigger filter is allowed only on advisory workflows; a required one needs the always-running decide job.
- `stacks-bench-smoke.yml` (advisory; PRs touching `examples/stacks-bench/**` except Markdown, weekly, manual) — `npm ci` + production build of the nine full-stack benchmark arms from their own lockfiles and the correctness gate (`bun gate.ts`) on each, the zero arm from npm and again from the workspace. Linux only, no timing and no load generator: it keeps the public benchmark re-runnable, it measures nothing. The arms are outside the bun workspace, so no other job installs or builds them.
- `real-bench-app-smoke.yml` (advisory; PRs touching `examples/real-bench/app/**` except Markdown, weekly, manual) — `npm ci` + production build of the catalogue-app arms from their own lockfiles, the pyreon arm from the workspace, and the correctness gate (`bun gate.ts`) on each. Linux only, no timing, no throttle, no memory reading: it keeps the arms buildable and correct. The arms are outside the bun workspace, so no other job installs or builds them.
- Native lane selection follows package-owned lowering as well as the PMTC
  directories. `native-surface-touched.ts` recognizes plugin source and its own
  selector scripts; `native-plugin-surface.ts` derives the runtime import closure
  from declared plugin exports using Bun alone, before installation. Shared
  helpers and their resolution manifests select every device app. Deleted,
  unreadable or unresolved dependencies, computed imports and CommonJS loads
  fail closed. Ordinary unrelated web source and the JSX compiler's Rust crate
  remain outside this native surface. A changed manifest skips only when both
  current and comparison-base metadata are web-only; PR merge checkouts retain
  both parents so removing a custom plugin declaration still selects the lanes.
- **A macOS job starts only when the change can reach what it reads** (`scripts/native-surface-touched.ts`, `scripts/native-workflow-surface.ts`). macOS runners are about three concurrent; on 2026-11-16 three jobs ran while eight queued and GitHub cancelled short ones as "not acquired by Runner". The contract:
  - `Validate emitted Swift (real-SDK typecheck, macOS)` is gated by its own decide outputs `macos` (path classifier, `classifyMacosLane`) and `graph-macos` (the native-compiler dependency graph computed WITHOUT workflow files). The Linux `Validate emitted Swift + Kotlin` keeps the older `run`/`graph` outputs, so its behaviour did not narrow. Android Gradle configuration (`examples/native-*-android/` `build.gradle.kts`, `settings.gradle.kts`, `gradle.properties`, `gradle/`, `gradlew`) starts no macOS job: no macOS-run test reads it. An Android `scripts/*.sh` or `androidTest` Kotlin file does (the example-compile and intl-differential tests read them) and still starts it.
  - An edit to a workflow file starts a macOS lane only when that lane's own job block changed, compared at the base and the head, together with the top-level `env`/`permissions`/`defaults` it inherits and the `scripts/…` files and local actions the block names. Comment-only edits do not count (a `#` line inside a `run: |` block does). Another workflow file (a Dependabot action bump in `ci.yml`, a trufflehog pin) starts nothing. The graph computation drops every `.github/workflows/` path: `ci.yml` is a root file to `affected.ts` and used to escalate the macOS typecheck to `--filter=*`.
  - `iOS — xcodebuild` is selected for an edit to `native-device.yml` only when the `ios-build` block (or the inherited sections) changed, and the Android lane likewise for `android-build`. `native-inputs-fingerprint.ts` hashes each platform's own job block into that platform's apps instead of the whole file, so a decide-job, comment or other-platform edit moves no app.
  - Fail-closed: only a computed `false` skips. An empty file list, a missing or unreadable base or head, a job id that is not found, a manifest that does not parse, an unknown path and any thrown error run the job. The skip path is the existing one: the job's `if:` is false, it reports `skipped`, and a skipped required check counts as success. Required job names are unchanged and locked by `native-macos-lane.test.ts`, which also pins the shape the workflow reader depends on (2-space `jobs:` children).
  - The macOS typecheck also skips for: an `examples/native-*-ios/iosUITests/**` or `examples/native-*-android/app/src/androidTest/**` file that still exists at the head (the suite only checks those directories exist, plus reads `IntlDifferentialCases.kt` by name, which still starts it; a deleted file starts it too), and a `bun.lock` / root `package.json` change that leaves the native workspaces' dependency closure and the root `overrides` identical and changes the root manifest only in `scripts`, `version`, `description`, `keywords`, `repository`, `homepage` or `bugs` (`lockfileInertForNative`, the same closure the device fingerprint hashes). A root dependency change always starts it.
  - Not narrowed on purpose: a change to a `decide`/`changes`/`fingerprint` job alone does not start a device lane (its effect is visible in that PR's own run), and the Linux `Validate emitted Swift + Kotlin` job keeps the whole-file rule.
- `codeql.yml` — `Analyze (javascript-typescript)`.
- `cancel-conflicting-ci.yml` (push to main + every 30 min):
  - cancels in-flight runs of PRs that became conflicting. GitHub never dispatches for a conflicting PR, but does not stop a run already in flight. Only a definitive `CONFLICTING` is acted on; `UNKNOWN` is skipped; a failed listing aborts.
  - prunes superseded cache generations on main (`scripts/prune-superseded-caches.ts`).
- The Android Gradle dependency cache (`gradle-deps-<os>-<hash of the native examples' gradle files>`) is written ONLY on `main`, ONLY on a restore miss, and its key carries no `run_id` — a run-id suffix once kept four identical ~650 MB copies and pushed the repo to 10.39 of its 10 GB, LRU-evicting the small bootstrap caches every lib-needing job depends on. `gradle-deps-` is a pruned family in `prune-superseded-caches.ts`.
- `required-check-autoheal.yml` — listens to `Native Device Build` and `Native Compiler Validation` and re-runs (`rerun-failed-jobs`, so a green sibling job is not repeated) a completed pull_request run at `run_attempt` 1, with a PR comment naming the cause, in two cases: the run concluded `cancelled`; or it concluded `failure` but EVERY non-successful job never started (conclusion `cancelled`, zero steps, check-run annotation "The job was not acquired by Runner of type hosted even after multiple attempts" — GitHub never assigned a macOS runner, observed 15 minutes after queueing). One genuinely failed job anywhere (a mixed run included) means no rerun: a real failure stays red. Also skipped when the PR head is no longer the run's SHA or a newer run of the workflow exists. Uncertainty (no PR, annotation unreadable) fails closed. The decision script is exercised by `packages/internals/test-utils/src/tests/required-check-autoheal.test.ts`; a `workflow_run` workflow runs only from `main`, so an edit cannot be exercised on its own PR.
- `leak-sweep.yml` (advisory) — least-squares heap slope over the perf-dashboard journeys, dev mode only (counters tree-shake in production). A journey over the threshold runs confirmation cycles and is flagged only if the heap keeps growing through them: one allocation step (a hash table doubling once) reads as a slope of a tenth of its size over 15 samples. Rule and derivation: `scripts/perf/leak-verdict.ts`. Locally: `bun run perf:leak-sweep`.
- `docs-freshness-guard.yml` (push to main, not a PR check) — reruns `gen-docs` + `docs/scripts/gen-all.ts`. Drift from two concurrent merges reds the offending commit and opens or updates an `auto/docs-regen` fix PR (with a changeset when mcp `api-reference.ts` drifted; automerge when `RELEASE_PAT` is set).
- `published-state.yml` — daily repo-vs-npm check.

## Red default branch alarm

A red run on the default branch gates nothing and nobody watches the Actions tab: `Coverage (Full)` was red on 14 consecutive pushes (2026-11-11 21:00 UTC until #4492 on 11-16) before anyone noticed, and the nightly `Leak Sweep` had reported a leak on five consecutive nights (from 2026-11-12) when this was written. `main-red-status.yml` keeps ONE sticky issue per workflow, `[main] <workflow name> is red`.

- **Opens** when the newest run of that workflow with a verdict on the default branch is red (`failure`, `timed_out`, `startup_failure`, or a job cancelled at its own `timeout-minutes`). The issue names the workflow, the first red commit, the last green commit and the compare link between them (from the workflow's last 100 runs on the branch), and each failed job with its failed step.
- **Comments** once per further red commit. A re-run or a schedule on a commit already named adds nothing; a commit whose own event was lost is named by the next event.
- **Closes** on the next green run of that workflow, with a comment naming the commit. A re-run to green closes it too.
- **No verdict** (neither opens nor closes): a run cancelled because a newer push superseded it, a run cancelled by hand, a skipped run, a run in progress. The state is always the NEWEST run with a verdict, so an old run finishing late cannot reopen or close anything. A job cancelled by its own timeout is told apart from an outside cancel by GitHub's annotation "has exceeded the maximum execution time" (the run reads `cancelled` in both cases).
- Pull request runs never start it (`branches: [main]` on the trigger, and the job also requires a non-pull-request event on the default branch).
- **The watch list is gated.** `workflow_run` takes workflow names and no wildcard. `scripts/check-main-red-watchlist.ts` (validate-fast, and `Fast Gates` through the ci-complement step) fails when a workflow file is neither named in the list nor exempt in that script for a reason it verifies from the file: `self`, `pull-request-only` (every trigger is a pull request event), `acts-on-pull-request-runs` (a `workflow_run` follower whose jobs all require a pull request run). It also fails on a watched name no file carries, which is what a rename leaves behind. **Adding a workflow means adding its `name:` to the list.**
- It overlaps on purpose with the two specific notifiers: a size-ceiling breach also opens `[main] CI is red`, and a red nightly device build also opens `[main] Native Device Build is red`. The specific issue says how to fix that failure; the general one says since which commit.
- Tests: `main-red-status.test.ts` executes the workflow's real script against recorded run, job and annotation shapes; `check-main-red-watchlist.test.ts` covers the gate. A `workflow_run` workflow runs only from the default branch, so an edit to it cannot be exercised on its own pull request: after merging one, read the first `Default Branch Status` run.
## What keeps the default branch green

Protection is non-strict and there is no merge queue, so a pull request is tested against the base it was pushed on, not against the default branch it merges into. Each breakage of 2026-11-10 → 11-17 was green on its own pull request. Where the gate now sits:

| Class | What happened | Caught on the pull request by | Still only caught after merge |
| --- | --- | --- | --- |
| a. Summed size growth | Several PRs each under budget; the sum crossed a ceiling. Same disease, 2026-11-17: a KB constant in `e2e/site-home.spec.ts` that `main` sat 31 B under failed three unrelated PRs | By design nothing: a PR is judged on its own bytes (`PYREON_SIZE_MODE=pr`, #4490; the site's pages the same way in `Check Site Route Budgets`) | The sum, on `main` (`size-ceiling-status.yml` issue). Does not block unrelated PRs |
| b. Coverage under a floor | #4422 and #4481 lowered five packages; `Coverage (Full)` red on 14 consecutive pushes | `Coverage (changed packages)` in `Build` now counts measured packages (not examples or docs) and measures up to 30. Both PRs had 25 and were skipped by the old 15-workspace count | A PR with more than 30 directly changed packages (it prints a warning and a job summary naming them); `@pyreon/native-compiler` (measured by `Coverage (Native)` on `main`); a test that fails only under the four-package pool |
| c. A ratchet baseline measured before other PRs landed (#4479) | The baseline and the code it measures arrived in different PRs | Nothing can: it is a property of two PRs together | Always. The next PR's `Fast Gates` goes red, and `[main] CI is red` opens |
| d. A git-merged generated baseline (#4520) | `total` 3403 beside entries summing to 3405 | Each ratchet script checks its own baseline first (`scripts/baseline-total.ts`): `total` equals the sum, and the per-file baselines are byte-identical to the generator's output (`generator(parse(file)) === file`; the readable baselines record no `total` at all, see below). They run in `Fast Gates`. And `affected.ts` now selects `@pyreon/test-utils` for the file | — |
| e. A test merged while the contract test forbidding its shape was in another open PR | Two PRs, each green alone | Only if the second PR's CI runs after the first merged (its merge ref then contains both) | When the second PR was already green: it merges without re-running |
| f. A test that times out only under `Coverage (Full)` load | charts M4 fuzz, 60 s | `Coverage (changed packages)` runs the same instrumented suite, but alone, so load-only timeouts pass there | The four-package pool on `main`. `check-coverage.ts` prints `slow under coverage:` for any test of 5 s or more |

#### The two readable baselines: who tightens, and when

`readable-baseline.json` and `readable-oxlint-baseline.json` hold the static description plus ONE LINE PER FILE and nothing else: no recorded `total`, no file count, no timestamp. A shared line that every change rewrites made every open PR conflict on it (seven PRs, twice in one hour, 2026-11-17), and a conflicting PR gets no CI; the size budgets had the same disease before they were split per package (#4490). Now two PRs that change different files' entries merge without a textual conflict. The totals are summed when the gate prints.

- An ordinary PR does not need to touch either file. Fewer findings than the baseline pass; a loose baseline is harmless.
- `--update` only tightens. Whoever removes findings may run it in the same PR (their lines are per file, so it conflicts with nothing unrelated). Nobody has to.
- Raising needs `--allow-raise` and is for a file that predates the ratchet (or a renamed or moved file). Never to absorb a finding the PR's own code added.
- When merging the default branch into a PR, take the default branch's copy of both files (`git checkout origin/main -- readable-baseline.json readable-oxlint-baseline.json`), then run both ratchets.
- Both scripts refuse a file that is not exactly what the generator writes for its own parsed content (unsorted, reformatted, duplicated line, reintroduced `total`, edited description).

Classes c and e, and the residue of a and b, are closed only by testing the merge RESULT before it lands. Until then the backstop is `main-red-status.yml` ("Red default branch alarm"): one run, not days.

All of these are watched by the alarm (`main-red-status.yml`).

### Testing the merge result: the two options, measured

Measured 2026-11-10 → 11-17: 9 to 52 merges a day (41, 52, 13, 13, 9); a successful PR run of `ci.yml` is 6 to 18 jobs that execute, 16 to 93 runner-minutes, and 12 to 79 minutes of wall clock with the slowest job waiting 0 to 47 minutes for a runner (ten runs sampled on 2026-11-17, 24 runs queued at the time). Runners: 20 concurrent Linux jobs, about 3 macOS; the iOS job is 65 to 80 minutes.

| | Strict protection (PR must be up to date) | Merge queue (with light PR CI) |
| --- | --- | --- |
| What it tests | Each PR against the exact base it merges into | Each group of up to 5 PRs against the base plus the group |
| Cost per merge | Every merge makes every other open PR stale. Each needs an update push: a full PR run (about 30 jobs, 16 to 93 runner-minutes, plus the native lanes when selected) | One full `ci.yml` run per GROUP (65 to 85 runner-minutes over about 20 jobs), shared by up to 5 PRs; the macOS and device lanes are skipped in the queue |
| Throughput | Serial: one merge per PR run. At the measured 12 to 79 minutes that is 18 to 120 merges a day with nothing else queued, and a native PR adds 65 to 80 minutes per merge (18 to 22 a day). The 41 and 52 merge days do not fit | 3 groups at once, 5 PRs each, 10 to 24 minutes on idle runners and 64 under load: several hundred merges a day in principle |
| Known failure here | Not tried. With N green PRs waiting, N−1 of them re-run for each merge: about N²/2 runs to land N | Tried 2026-11-11 without light PR CI: about 120 queued runs, a group waited in the same line, no PR merged in 4 hours |
| Does not cover | Nothing the PR run covers is lost | macOS typecheck, iOS and Android (skipped in a group); `Coverage (Full)` |

## Merge queue

Tried 2026-11-11 and switched off again the same day (ruleset 19416270 has no `merge_queue` rule): with the org's 20-concurrent-job limit and about 120 queued runs, a group's own CI waited in the same line as the PR runs, the oldest group needed more than 5 hours, groups were rebuilt twice, and in 4 hours no PR merged, while the same green PRs merged immediately without the queue. Try it again only with more runner capacity. Prepared, not enabled: `merge_group` events never fire without the rule. Every workflow that owns a required context carries `merge_group`:

| Context | Workflow / job | In a merge group |
| --- | --- | --- |
| `Install`, `Fast Gates`, `Build`, `Test`, `Test (browser)`, `Release Build`, `bootstrap-exit-codes` | `ci.yml` | Full matrix, as on `push: main`. Release Build audits advisories against `merge_group.base_sha` (pre-existing ones warn). Labels are absent, so `skip-release-readiness` does not apply, as on `main`. |
| `Changeset`, `Diagnose Catalog` | `pr-gates.yml` | Skipped: both depend only on the PR's diff and labels, which the PR already passed. |
| `Analyze (javascript-typescript)`, `CodeQL` | `codeql.yml` | Runs. `CodeQL` is posted by code scanning after the upload, so the job cannot skip. |
| `Validate emitted Swift + Kotlin` | `native-validate.yml` `validate` | Runs when the group's diff (`base_sha` → head) selects it, by the PR rules. |
| `Validate emitted Swift (real-SDK typecheck, macOS)` | `native-validate.yml` `validate-swift-typecheck` | Skipped. |
| `iOS — xcodebuild (Simulator SDK)`, `Android — gradlew assembleDebug` | `native-device.yml` | Skipped. |

- macOS and device lanes skip in the queue because they ran on the PR and a macOS slot wait (p90 144 min, 2026-11-10) at the head of the queue would hold every group behind it. The nightly runs re-prove `main`. To run them in the queue, remove the `merge_group` exclusion from their `if:`.
- Concurrency keys must be unique per queue ref: `github.event.pull_request.number` is empty in a merge group, so use `… || github.ref`. Never cancel a merge-group run (`cancel-in-progress` is PR-only everywhere).
- Do not save a cache from a merge group: its ref is deleted, so the entry only evicts others.
- `ci-main.yml` (`Coverage (Full)`, `Coverage (Native)`) has no `merge_group` trigger: neither is required, so in the queue it would cost about 18 runner-minutes per group for a verdict the queue does not read. Main's push run remains the backstop.

Enable (maintainer, one ruleset change):

```bash
gh api repos/pyreon/pyreon/rulesets/19416270 > rs.json
jq '{name, target, enforcement, conditions, bypass_actors, rules: (.rules + [{type: "merge_queue", parameters: {merge_method: "SQUASH", grouping_strategy: "ALLGREEN", max_entries_to_build: 3, min_entries_to_merge: 1, max_entries_to_merge: 5, min_entries_to_merge_wait_minutes: 5, check_response_timeout_minutes: 120}}])}' rs.json > rs-queue.json
gh api -X PUT repos/pyreon/pyreon/rulesets/19416270 --input rs-queue.json
```

- First canary: one docs-only PR (for example a one-line `.agents/` edit). It exercises the full `ci.yml` matrix, CodeQL with its `CodeQL` upload context, the skipped `pr-gates` jobs, the native-validate decide on a group diff and the skipped device lanes, without a 60-minute native lane. Watch that all 15 contexts report on the `gh-readonly-queue/main/…` head before queueing more.
- `SQUASH`: the only allowed method; keeps the required linear history.
- Build concurrency 3: a group costs about 65–85 runner-minutes over about 20 jobs (full `ci.yml`: 18 jobs, 57–61 min; CodeQL 4; Linux native validate 18 when selected). Three groups at their widest take most of the 20 org slots.
- Merge limits 1–5 with a 5-minute wait: about 25 merges a day; a busy hour batches 2–5 PRs into one full run.
- Timeout 120 minutes: a full `ci.yml` run takes 10–24 min on idle runners and up to 64 under load (2026-11-10); Linux job queue p90 was about 100 min.
- Contributors: the merge button becomes "Merge when ready"; auto-merge (`gh pr merge N --auto`) adds the PR to the queue once its checks pass. A group that fails removes its PR with a comment; fix, push, re-queue. `strict` stays off.
- Changesets: the Version PR and `auto/docs-regen` go through the queue like any PR (`gh pr merge --auto --squash` enqueues). The queue's fast-forward of `main` is a normal push, so `release.yml`, `docs.yml`, `docs-freshness-guard.yml` and main CI trigger as before.
- Roll back: `gh api repos/pyreon/pyreon/rulesets/19416270 | jq '{name, target, enforcement, conditions, bypass_actors, rules: [.rules[] | select(.type != "merge_queue")]}' > rs-noqueue.json`, then the same PUT with that file. Queued PRs leave the queue; `merge_group` triggers go dormant again. The UI path is Settings → Rules → Rulesets → main branch protection → "Require merge queue".

### Light PR CI

Inert until the repository variable `PR_CI_MODE` is `light`. Unset, or any other value, is exactly the behaviour above. Purpose: a PR runs about 8 jobs instead of about 30, and the full matrix runs once per merge group and on `main`, so the full verification applies to the merge RESULT (two individually green PRs can break `main` together because protection is non-strict) and costs one run per group, not one per PR.

The switch is `vars.PR_CI_MODE == 'light'` AND `github.event_name == 'pull_request'`. `ci.yml` resolves it once in `Install` (step `Resolve PR CI mode`, output `pr-light`); `native-validate.yml` reads the variable inline. A resolver failure leaves `pr-light` unset, which means the full run (fail-closed).

| Job | Normal | Light, on a PR | Light, in the queue / on `main` | Why |
| --- | --- | --- | --- | --- |
| `Install`, `Fast Gates`, `Test` (aggregator) | runs | runs | runs | cheap, and everything else hangs off them |
| `typecheck (…)`, `test (…)` cells | affected-filtered | same | full | already affected-filtered on a PR; the unit tests are the main PR signal |
| `bootstrap-exit-codes` | only when `bootstrap.ts` changed | same | same | rare and about 8 min at most |
| `Changeset`, `Diagnose Catalog` | runs | runs | skipped | functions of the PR diff and labels; a group cannot decide them |
| `Analyze (javascript-typescript)`, `CodeQL` | runs | runs | runs | about 4 min; security feedback stays on the PR |
| `Validate emitted Swift (real-SDK typecheck, macOS)`, `iOS — xcodebuild`, `Android — gradlew` | selected by paths | same | SKIPPED | the PR is their ONLY coverage (the queue skips them), so light mode must not skip them |
| `e2e (…)` | affected suites | skipped | full | HEAVY, runs in the queue |
| `Scaffold Smoke (…)` | when selected | skipped | full | HEAVY, runs in the queue |
| `Build` (verify-modes, budgets, coverage floor, rust equivalence) | code PRs | skipped | full | HEAVY, runs in the queue |
| `Test (browser)` | code PRs | skipped | full | HEAVY (timeout 35 min), runs in the queue |
| `Release Build` | code PRs | skipped | full | HEAVY, runs in the queue |
| `Validate emitted Swift + Kotlin` (Linux) | when the native selectors fire | skipped | when the group's diff selects it | HEAVY (about 18 jobs when selected), runs in the queue |

How `e2e` and `Scaffold Smoke` skip: `Install` reports them as unselected (`e2e-has` / `scaffold-has` = `false`, matrices `[]`), the same path a docs-only PR takes, so `scripts/ci-aggregate.ts` accepts their absence and `Test` stays a real verdict. `Build`, `Test (browser)` and `Release Build` carry `needs.install.outputs.pr-light != 'true'` in their `if:`. Concurrency keys and `cancel-in-progress` are unchanged.

A skipped job reports `skipped`, and a skipped required check counts as passing (GitHub, "Troubleshooting required status checks": a job skipped by a conditional reports Success; a workflow skipped by a trigger filter stays Pending, which is why the required workflows keep unfiltered triggers and skip per job). This guide already relies on the same behaviour for `Changeset` and the device lanes in the queue. NOT verified on this repository in light mode: the first light PR is the proof; see the checklist.

Rules the static gate (`scripts/check-light-pr-ci.ts`, in `validate-fast`) enforces: every workflow that owns a required context has `merge_group`; a job that uses the light condition has `merge_group` and `push` coverage and does not exclude `merge_group` in its own `if:`; a job the queue skips (the table's SKIPPED rows and their `changes` / `fingerprint` helpers) never uses it; a direct `PR_CI_MODE` read is bounded to `pull_request`.

Flip (maintainer). The queue MUST be on first: in light mode a PR's heavy results come only from the queue, so without it a PR would merge with `Build`, `Test (browser)`, `Release Build` and the e2e suites never having run.

```bash
# 1. queue on: the ruleset command under "Enable" above
# 2. then:
gh variable set PR_CI_MODE --body light
```

Roll back (seconds, no code change): `gh variable delete PR_CI_MODE`, then remove the `merge_queue` rule (see "Roll back" above). PRs pick the variable up on their next push or re-run; an already-finished run keeps its result.

First-run checklist, on the first PR after the variable is set:

- `Install` log shows `PR_CI_MODE=light`; the PR shows about 8 jobs and all 15 required contexts are present (green or skipped), none `Expected`.
- `Test` is green with `e2e` and `Scaffold Smoke` absent (it reports unselected, not failed).
- Queue it: the group runs the full matrix and all 15 contexts report on the `gh-readonly-queue/main/…` head. Watch queue wait: a full group is 65-85 runner-minutes; if it starves again (see the 2026-11-11 history above) roll back.
- A PR that breaks only a heavy job merges to the queue and fails there, removing itself with a comment: expect the failure feedback to arrive later than before.
- Known residual risks: the device lanes and macOS typecheck still run per PR (5 macOS slots); the queue skips them; `Coverage` stays main-only.

## Caches

- Downstream `node_modules` restores use the exact lockfile key only. A broad prefix downloads a tree the clean-install fallback must immediately discard to avoid stale peer resolution. The bun tarball cache still uses a prefix safely. The setup action exposes whether it already restored tarballs so scaffold jobs do not download the same store twice.
- Scaffold CI restores this commit's libraries through setup-pyreon, then sets `PYREON_BOOTSTRAP_SKIP=1` for the smoke step. Each temporary app otherwise changes `bun.lock`, invalidates bootstrap's global hash, and rebuilds every package again. This skips only the root bootstrap; generated-app installs, dependency lifecycle scripts, builds and smoke assertions still run. Local scaffold runs keep the default bootstrap behavior.
- `bun-install-cache-<os>-<lockhash>`: `Install` saves it on main. A PR whose `bun.lock` differs from the base saves its own; everyone else only restores.
- The macOS native lanes restore and save the content-addressed verdict store, like their Linux twin.
- `native-validate.yml` hydrates the verdict store from TWO restores, as a union: the default branch's newest store, then the ref's own on top (`snapshot-native-verdict-cache.ts … --merge`). Actions searches the current ref's caches before the default branch's, so one prefix restore gave a pull request its own older store and never main's newer one. Main saves under the `validate` lineage and every other ref under `validate-branch` (`VERDICT_LINEAGE`); the two key prefixes must not be prefixes of each other, or the first restore stops reaching main. Saving never merges: the archive is rebuilt from the live store. `check-ci-fail-fast` rejects a second restore whose hydrate lacks `--merge`.
- A verdict store is only as warm as the newest default-branch run that FINISHED. After a merge that changes a stub, the chart engine or the emit, every pull-request run that starts before main's run saves recompiles the same delta. The suite's cold speed is the only lever for that window.
- Native-validate job timeouts are the sum of each step's worst MEASURED time, times the measured runner-speed spread; the parts are listed beside each `timeout-minutes`. The uncached nightly has its own, larger budget per job, because it compiles everything. Re-derive from the parts when a step is added or the suite's concurrency changes; never raise a cap without the measurement that justifies it.
- `native-validate.yml` builds `lib/` with `PYREON_BOOTSTRAP_SKIP_NATIVE=1`: no step there runs the JSX compiler's Rust backend, and its binary is in no cache those jobs restore, so `cargo build` ran from nothing on every run (37-47 s on ubuntu, 57-67 s on macOS).
- Native workers write `.cache/pyreon-native-validate`; Actions archives only `.cache/pyreon-native-validate-archive`. Hydrate before tests and snapshot complete atomic JSON verdict/probe records before every save, including cancellation paths, with `scripts/snapshot-native-verdict-cache.ts`. Preserve both the root compiler store and the `kotlin-runtime/` co-source/runtime store without flattening their namespaces. Every verification step uses the same cache directory and disables reads/writes on the nightly drift run. Workers can outlive a cancelled test step, and GNU tar rejects a directory that changes while it reads. A green cache action can hide a failed upload warning: confirm the log's saved key and the cache API entry. Changing the archived path changes Actions' cache version, so the first run of this format is cold; keep restore/save paths aligned across all native lanes.

## Gate reference

- **Coverage (Full)**: main measures every testable workspace except the native compiler, which retains its separate cached coverage job. Coverage-infrastructure PRs also run the full gate before merging. The four-worker pool is followed by three serial nested-build suites; budget for both phases. The full job has a 35m backstop, a 25m coverage step and a 3m always-run log upload. Each package logs its start and duration, so a partial run identifies work still in flight. Per-package deadlines terminate the owned POSIX process group (TERM, then KILL after 1s) and settle even if inherited pipes stay open. Timed-out/signalled executions fail even after printing a summary. No package thresholds are relaxed. Optional native binaries must not control JavaScript fallback coverage: syntax, live-option and lens assertions run independently, with Rust parity checked additionally when the binary is installed.
- **audit-types** (`bun run audit-types --all --strict`): flags public-interface fields with zero non-type references (typed-but-unimplemented). New HIGH findings block. Fix the runtime, or add to `EXEMPT_FIELDS` in `scripts/audit-types.ts` with a rationale.
- **verify-modes** (`bun run verify-modes`): `vite build` for every example × mode, asserting rendered content, not just a green build. New cells must check content.
- **Size gates** (`Check Bundle Budgets`, `Check Import Budgets`, `Check Route Budgets`, three steps of `Build`): gzipped main-entry size per published package, canonical minimal-import scenarios, and first-load JS per `ssr-showcase` SSG route. All measure built output with a `NODE_ENV=production` define; rules in `scripts/size-budget-policy.ts`, ceilings in `scripts/size-budgets/` (`packages/<name>.json` holds a package's `bundle` and `imports`, `apps/<example>.json` its `routes`; one file per owner, so PRs on different packages never touch the same file).
  - **Pull request (`PYREON_SIZE_MODE=pr`)**: judged on the bytes the PR adds. `Prepare size base` runs `scripts/size-base.ts`, which measures `HEAD^1` of the merge ref (the commit the PR merges into) with the head's scripts in a worktree. An entry fails when it grew by more than 2% of its base size (floor 64 B) without the PR changing that entry's ceiling, when the PR added bytes to an entry that ends over its ceiling, or when it has no ceiling. An entry already over its ceiling on the base that the PR did not grow passes with a note. A missing base file fails all three steps.
  - **Push to `main` and merge queue (`PYREON_SIZE_MODE=main`)**: every entry against its ceiling. This is where the sum of several merges shows: `Build` goes red on main, `size-ceiling-status.yml` opens the sticky issue `[size] main is over a size ceiling` and comments on every further red run, and PRs that add to the entry fail until it is settled. The issue closes on the next run where all three steps pass.
  - **Local (no mode)**: build and measurement failures and missing ceilings fail; over-ceiling entries are printed, not failed, because a local run has no base and cannot tell its own growth from main's. `--mode=main` gives the ceiling verdict.
  - **Accepting growth**: `--update=<id>` on the matching gate writes `ceil(measured × 1.10)` to that entry's file; the edit in the PR diff is the acceptance. Unscoped `--update` only seeds new entries and raises ones already over; it never lowers. Rebuild each changed package before measuring locally: source-resolving tests can pass while these gates measure yesterday's `lib/`.
  - **Cost**: the base is rebuilt only when a changed path can move a size (`movesLibSizes` / `movesRouteSizes`); it reuses the head's `lib/` and rebuilds the packages whose sources differ. No extra job or runner slot.
- **Site route budgets** (`Check Site Route Budgets`, a step of the `e2e (…)` cell that ran the `docs` suite; `bun run check-site-budgets`): the JavaScript each budgeted pyreon.dev page requests on load, the fourth size family under the same policy and the same three modes as the size gates above. Ceilings: `scripts/size-budgets/sites/docs.json`, one line per page; that file is also the list of pages measured.
  - **What is measured**: `e2e/site-sizes.measure.ts` loads each page of the built site in Chromium at 1440×900 without scrolling and sums every script it requested, gzip -9 (entry, island hydration, islands in view or loaded on idle, idle prefetches). `(shell)` is read from the build with no browser: the entry, the nav island and the copy button with their static import closures. Noise band: `ROUTE_NOISE_BYTES`.
  - **Pull request**: `--mode=pr --base-ref='HEAD^1'`. The gate builds the commit the PR merges into in a worktree (`scripts/size-base-tree.ts`: the head's `lib/` and dependencies, an incremental bootstrap, one site build) and measures it with the head's measuring spec. It builds nothing there when no changed path can move a page (`movesSiteSizes`: anything that moves a `lib/`, or anything under `docs/`). The job's checkout is `fetch-depth: 2` for that `HEAD^1`.
  - **Push to `main` and merge queue**: `--mode=main`, every page against its ceiling; a breach is the fourth step `size-ceiling-status.yml` reads.
  - **One source of truth**: the site e2e specs assert what a page may load (no router app, no stylesheet of another section, no preload outside the entry graph), never a byte count. `site-budgets.test.ts` fails a `*_BUDGET_KB` constant reappearing in them.
  - **A ceiling whose page was not measured fails in every mode**: the page is not in the build. The old spec held a number for `/blog/tags/signals`, a page that was never built; its test loaded the 404 page and passed.
  - **Not every package is a trigger**: the step runs where the `docs` suite runs, and `e2e-affected.ts` selects that suite for the render core, the compiler, zero and the site's own code, not for every package a demo imports (`@pyreon/form`, the styling runtime). Bytes from those packages reach the pages unjudged on their PR and show on `main` (class a).
  - **Accepting growth**: `bun run check-site-budgets --update=docs:<route>` (also how a new page is added) writes `ceil(measured × 1.10)`. CI builds the site with the JS compiler backend; a local build with the native binary measures a few bytes apart, inside the noise band.
- **Lighthouse check** (job `lighthouse` in `docs.yml`, after `build`; `deploy` does NOT need it, so no Lighthouse result can hold back a pyreon.dev deploy or the scheduled blog publish; locally `cd docs && bunx vite build && bun run lighthouse`): `docs/scripts/lighthouse.ts` runs Lighthouse 13.6.0 (`LIGHTHOUSE_VERSION`; CI installs it with `npm ci --ignore-scripts` from the integrity-pinned `scripts/lighthouse-tools/package-lock.json`, outside the bun workspace, so its ~60 dependencies are not in every install and `bun.lock` never lists them; a local run without `PYREON_LIGHTHOUSE_BIN` uses `npx lighthouse@<version>`; bump the version, the tools lock and the test that keeps them equal together, on purpose, since a new version can add audits) against the built site served the way GitHub Pages serves it (`docs/scripts/lighthouse-server.ts`: gzip, `max-age=600`, `/dir` → 301 `/dir/`, `404.html`), on `/`, `/docs/getting-started/` and `/products/reactivity/`, 5 runs each, Lighthouse's default mobile config (the one PageSpeed Insights reports), a fresh Chrome per run.
  - **Hard, deterministic**: Accessibility, Best Practices, SEO and Agentic Browsing exactly 1 on every run, with every audit that counts towards the score passing (weight > 0, not informative, manual or not-applicable). Across 4 CI attempts (60 runs, runner benchmarkIndex 1854–2771) these never varied. Plus a page proxy read from the built HTML: no empty CSS rule block (`sel { }`) in a page's inline styles (`pageProxies`).
  - **Report-only, timing**: the median performance score and per-metric medians (`PERFORMANCE_FLOOR` 0.99, `METRIC_BUDGETS` FCP 1500 / LCP 2000 / SI 2500 / TBT 150 ms / CLS 0.02) go to the job summary and to `medians.json` in the `lighthouse-<attempt>` artifact (kept 90 days: the trend). `--perf assert` makes them fail locally. They are not a CI gate because they do not hold still: the same build gave the docs page per-run TBT 39/134/99/180/0 ms on one runner, a median score of 0.99 there and 1 on three others; a floor of 1 failed one attempt in four with nothing changed, and Chrome is the runner's (unpinned).
  - **CPU calibration**: Lighthouse's 4× slowdown is calibrated for a host whose `benchmarkIndex` is 1500–2000; a current laptop measures ~3700, so 4× there emulates a much faster phone than PageSpeed Insights does. `--cpu auto` (default) reads the host's `benchmarkIndex` from one discarded run and uses `4 × benchmarkIndex / 1750`, never below 4 (`calibratedCpu`).
  - **What it cannot catch**: a 98 → 100-class performance regression. The pre-fix site scored a median 100 at the calibrated setting; PageSpeed Insights' hosts are slower (`--cpu 16 --latency 170` on a ~3700 host reproduced its 98). That class is covered by deterministic proxies instead: no empty CSS rule blocks (this check); no computed-style read during island setup (`server/src/tests/island-visible-targets.test.ts`, "reads no computed style until the observer reports"); an eager theme pair never eager-loads both files (`docs/src/site/tests/media-priority.test.tsx`); the JavaScript each page requests (`Check Site Route Budgets`, above). Use `--cpu 16 --latency 170`, or PSI after a deploy, to check headroom by hand.
  - **Reports**: every run's JSON, `medians.json` and the log are in the `lighthouse-<attempt>` artifact.
  - **`lighthouseLlmsTxtFailures` is a hand copy** of the pinned audit's checks (`@pyreon/test-utils/llms-txt`), so the unit tests can run without Lighthouse. It can drift from the real audit after a version bump; the CI job runs the real audit on the served `/llms.txt` every run, and is what catches that drift. Re-copy the checks when bumping.
- **check-distribution**: every published package declares `sideEffects`, ships source maps, and excludes the `lib/analysis` bundle report (live `npm pack --dry-run` probe).
- **check-css-balanced**: every git-tracked `.css` file closes every block it opens (comments and strings skipped). CSS closes an open block silently at end of file, so a `}` lost in a merge passes every unit test while the rules after it move into the open block, and any stylesheet a bundler concatenates after it nests there too (`vite build` then fails in lightningcss). `@pyreon/calendar` 0.53.0 shipped exactly that.
- **check-esm-only**: Pyreon ships ESM only. `require` and `default` export conditions are both banned in every published package — `default` lets `require('@pyreon/x')` resolve, which is what the policy forbids. The one exemption is `@pyreon/storybook` (Storybook's preset loader resolves through CJS), pinned by `shipped-preset.test.ts`. Accepted cost: Pyreon is absent from CJS-only toolchains, so `contrib/moltar/` is bun/deno only.
- **check-doc-claims**: numeric claims in docs must match source. The guarded claim sites live in the `checks` table in `packages/tools/cli/src/doctor/gates/doc-claims.ts`. Write exact numbers there, never "33+", and do not restate a count anywhere unguarded.
- **check-license-coverage**: every workspace (packages, examples, docs, contrib) carries the root `LICENSE` byte for byte and declares `"license": "MIT"` (`--fix` copies and normalises). It also scans every runtime dependency of every published package: strong copyleft (GPL/AGPL/LGPL/SSPL/BUSL) fails; weak copyleft (MPL/EPL/CDDL/EUPL) fails unless disclosed in `THIRD-PARTY-NOTICES.md`; a dual licence is classified by its weakest half. An absent install store skips the dependency scan loudly.
- **check-stability-tier**: the 1.0 semver contract. Every published package (plus the 7 compiler binaries) declares `"pyreon": { "stability": "stable" | "experimental", "experimentalSubpaths"? }` in `package.json`; the README status line is generated from it (`--write`), as are the docs `<PackageBadge>` and the tier table on `stability-and-direction.md` (`docs/scripts/gen-package-stability.ts`). It also fails a Stable package with a required dependency on an Experimental one (unless only its own experimental subpaths import it, or a reasoned `DEPENDENCY_ALLOWLIST` entry covers it; stale entries fail), `@pyreon/meta` re-exporting an Experimental package or a `_` name, and a `@deprecated` JSDoc tag with neither a manifest entry carrying `removeIn` nor a reasoned `DEPRECATED_ALLOWLIST` entry (stale entries fail). A private package (`@pyreon/auth` until it is published) must carry no tier field and no README status line: it makes no promise, the badge says "unpublished", and nothing else would check the field.
- **check-native-coverage**: the registry of every package that should reach iOS/Android, each pinned to how it crosses (`pmtc-lowers` = a representative snippet lowers for both targets with zero warnings; `native-container`; `webview-host`). `check-multiplatform-tier` only proves a story is declared; this proves it is true. Companion `check-native-lifecycle-wiring` requires every native container exposing `start()`/`connect()` to be auto-started by both emits or registered manual with a rationale (a never-called `start()` ships frozen at its initial value).
- **check-manifest-depth**: ratchet on MCP `get_api` density for locked packages.
- **Diagnose Catalog**: a new or edited user-visible error or warning message in `packages/core/{runtime-dom,runtime-server,core,compiler,router}/src/` must be matched by an `ERROR_PATTERNS` entry in `packages/core/compiler/src/diagnose.ts` (an existing one, or one the PR adds), or the PR carries the `skip-diagnose-catalog` label. The gate reads the messages out of the base and HEAD content of each changed file, so a perf-only change or a moved/reformatted message demands nothing. `diagnoseError` + `ERROR_PATTERNS` live in the browser-safe `@pyreon/compiler/diagnose` subpath with no `typescript` import, so the dev error printer can load them client-side. `compiler/src/tests/diagnose.test.ts` bundles the subpath and asserts no TS-API markers.
- **Release**:
  - Changesets fixed group (all packages share one version).
  - `check-release-readiness`: `publishConfig.access`, exact provenance repository identity and fixed-group coverage. The publisher shares the repository check and rejects the whole selected plan before any manifest rewrite or publish if its metadata is missing or mismatched.
  - Native coverage allows a cold verdict cache: a 60-minute measurement ceiling inside a 75-minute job, with per-compile and per-test deadlines still enforced. Stub/compiler changes invalidate cached verdicts.
  - `Release Build` and the publishing workflow reject high-severity locked dependency advisories through `scripts/audit-new-advisories.ts --level high`. On a pull request it also audits the base lockfile (`git show HEAD^1:bun.lock` into a temp dir with a stub `package.json` — `bun audit` reads only the lockfile) and FAILS only on advisories the PR introduces; advisories already on the base become `::warning::` lines, so one new upstream advisory can no longer red every open PR (that froze merges 2026-10-29 → 11-02). On `main` and in the release workflow it stays strict, and both steps of `release.yml` call the script (a bare `bun audit` there ignored the acceptance list). An advisory whose vulnerable range covers every published version cannot be cleared by a bump, so `scripts/advisory-acceptances.json` may record it with a reason: an entry holds only while the advisory's vulnerable range is unchanged (a fixed release changes it, and the gate fails again) and for at most 30 days, and an accepted advisory is still printed as a warning. Non-JSON audit output throws, so the gate fails closed. The wrangler `npm audit` in `Build` follows the same rule: it fails only when the PR changed `scripts/verify-modes-tools/package-lock.json`. The isolated Verify Modes workerd tool installs with `npm ci` from `scripts/verify-modes-tools/package-lock.json` and audits that tree too; update the lock together with its manifest. Its Sharp override pins the patched 0.35.5 transitive dependency while retaining the existing Wrangler runtime version and the high-severity audit.
  - `check-published-state`: every publishable package, not sentinels. A partial release where some packages lag the cut version is red and names each lagging package. Post-publish steps pass `--wait-for-publish`: only successfully submitted packages in the current `publish-result.json` receive a 5m visibility window before full verification; each lookup has a 10s bound and the step has 10m. Daily checks and resume detection stay immediate. This avoids treating npm processing delay as a failed publication.
  - `scripts/publish.ts` retries only npm errors with evidence of being transient (5xx, dropped sockets). Never 404/403/conflict, and never `E422 Error verifying sigstore provenance bundle`, which reproduces on every attempt (a manifest missing `repository` causes it).
  - `release.yml`'s `resume-detect` / `resume-publish` republish lagging packages from the release tag (never main), once per version.
  - A new package's first publish needs a one-time manual OIDC trusted-publisher bootstrap.

A comment that NAMES a script path makes it reachable, so reword rather than quote a path you do not want to drag in.

## Diagnosing slow CI

- Queue vs work per job: `gh api repos/pyreon/pyreon/actions/runs/<id>/jobs`. Exclude `conclusion == "skipped"`. `started_at − created_at` is queue; `completed_at − started_at` is work.
- A wall clock far above summed work, with queue in the hundreds of minutes, is slot starvation.
- Compare work separately from setup and queue time. Per-category and per-suite log groups delimit the work used to refresh `ci-batch.ts` profiles. Replaying old timings through new packing estimates balance; it is not a measured speedup. Validate with the next complete CI run and retain all selected work and the existing runner caps.
- Refresh profiles when timings drift. Do not automatically learn weights from partial or failed runs, and never use a timing estimate to decide whether a test runs.

## Browser and iOS runner reliability

- Before installing Linux browser dependencies, normalise the runner's regional Ubuntu archive URLs (any subdomain of `archive.ubuntu.com`: `azure.`, `<region>.ec2.`, a country mirror) to `https://archive.ubuntu.com` in `/etc/apt/sources.list`, every active `.list` or `.sources` file, and the local mirror lists those entries reference through `mirror+file:`. GitHub runners use `/etc/apt/apt-mirrors.txt`, so rewriting only source URLs leaves Azure selected. APT reads both formats; leaving one Azure entry active can stall `apt-get update` even while the official archive responds. Preserve suites, components and signing options. `set-ci-apt-mirror.ts` and the real install-entry regression cover mixed source formats, idempotence and failed setup.

- All Linux Playwright installs use `bash scripts/install-playwright.sh <engines>`. The OS-dependency timeout runs **inside sudo**, with SIGKILL for the whole process group at the deadline. A runner-owned timeout around Playwright cannot terminate its root-owned apt descendants, leaving a dpkg lock that poisons every retry. A TERM-then-KILL timer can also leave a resistant descendant if its immediate child exits before escalation. Repair interrupted dpkg before retrying or falling back; never remove lock files or kill unrelated package-manager processes.
- Chromium-only setup keeps the fallback to Ubuntu's preinstalled libraries. WebKit/Firefox dependencies and all browser downloads fail hard after bounded attempts. Downloads run as the runner user so they reconcile the restored browser store. Engine suites run only after successful setup; a setup failure already makes the required job red.
- `Test (browser)` has a 35-minute backstop derived from both setup budgets (10 + 16 minutes including retries/repair/download kill grace), test work and shared setup. Keep the outer timeout above the sum when changing any inner budget.
- iOS UI suites target the resolved simulator UDID with parallel testing disabled, so device state (appearance, location, URL delivery) belongs to the device configured by the workflow. Each app writes a separate `.xcresult` bundle (plus one per retry attempt, `<app>-attempt<N>.xcresult`), uploaded after success or failure. The exact `.ci-ios-results/*.xcresult` upload must enable hidden files because its result root starts with a dot; a completed or failed selected UI step with no matching results is an error, while entirely skipped app lanes do not upload.
- **Device-lane time budget** (`native-device.yml`, measured 2026-11-12 over six iOS and seven Android runs). iOS, 64–81 min: XCUITest execution is about 43 min of it (tasks 23–30, counter 9, router-demo 8, finance 2, todomvc 1), compiles about 13, the prelude 7–12, the device-SDK archive 2–5. One tasks test, `test_authGateStoreMutationAndTypedParamsDetail`, was 9–11 min of that (see the next entry). Android, 25–37 min: each of the five emulator steps cold-boots its own emulator (60–65 s each), and the todomvc step also runs R8 twice. The iOS job is the critical path of every native PR; Android finishes inside its queue wait.
- **Where XCUITest time goes** (profiled from the `t = …s` activity lines of job 133764838886, 2026-11-17; the profile of a run is its log, `gh api repos/pyreon/pyreon/actions/jobs/<id>/logs`). Three costs, none of them a sleep in the test source:
  - `waitForExistence(timeout:)` evaluates its predicate for the first time one second after the call. 427 of the job's 456 waits were answered by that first poll and took 487 s between them (tasks 184, router-demo 169, counter 91, finance 33, todomvc 9). The suites use a file-private `waitToExist(timeout:)` (same contract, asks at once, then every 0.1 s), held by `create-multiplatform/src/tests/ios-device-test-harness.test.ts`.
  - A scroll drag is 3–4 s on a local simulator and 6–7 s on the runner whatever its velocity (`.fast` moves the finger sooner and then waits for the page to stop), so the number of drags is the cost. The tasks gallery test crossed its page four times: 39 drags, 158 s in the gestures alone; visiting the page in its own order needs 19.
  - Every element read is an accessibility round trip whose cost follows the screen, not the query: 0.05 s on the tasks home screen, 0.3 s on the chart gallery (186 nodes against 54, but fifteen hosted WebViews). A scroll loop there read the target six times and the window six times per drag; it needs two reads, the ones that prove the page stopped.
  - Measured on an iPhone 17 Pro / iOS 26.5 simulator, three runs each: the gallery test 436, 436, 437 s before and 218, 217, 217 s after (2,714 logged activities against 1,774, the same 210 assertions); the tasks suite without `test_hostedEditorsRoundTrip` (it fails on that simulator before and after) 734, 802, 733 s before and 421, 420, 416 s after, the same 21 tests.
  - On the runner (run 44034514478, ONE run, no retries, 94 passed and 2 skipped as before): the job 51 min against 62–69 for the five green full runs before it; summed UI-test seconds 1,884 against 2,395–2,578 (tasks 923, counter 485, router-demo 308, finance 119, todomvc 49); the tasks step 17.7 min against 19.7–24.1; the gallery test 398 s against 522–687, still 22 drags at 4.2 s. The time-budget figures above predate this.
- **iOS UI tests run through `scripts/native-ios-uitest.ts`**, never bare `xcodebuild test -retry-tests-on-failure -test-iterations N`: with those flags one failing test re-ran the whole suite on every iteration (28, 56, then 84 results), which a 23–30 minute suite cannot fit in the job timeout. The script builds once (`build-for-testing`, never retried), tests once (`test-without-building`), then re-runs only the failed tests with `-only-testing:`, at most three runs per test; more than five failed tests in the first pass is a broad failure and is not retried. A skipped test (`XCTSkip`) is its own status, listed in the summary and never a failure, and xcodebuild's exit code is the verdict (the parsed names only say which tests to re-run). Every retry is a `::warning::` naming the test and a row in the job summary; a test that fails every attempt is an `::error::` naming it. The workflow keeps the literal `xcodebuild test` words so `check-ios-signing-policy` still sees each invocation. Contract tests: `native-device-reporting.test.ts`.
- **Every `xcodebuild` call passes `-derivedDataPath`** to a gitignored path inside the project (workflows, `*.sh`, and TypeScript spawns such as `pyreon-native dev`). Without it the build lands in `~/Library/Developer/Xcode/DerivedData`, outside the checkout, and outlives the worktree. `check-ios-signing-policy` (in `validate-fast`) fails a call without it.
- **A red Android emulator step is named by the `Name the failed Android tests` step** (`scripts/native-android-connected-failures.ts`, `if: failure()`): `gradle connectedCheck` prints only "There were failing tests" and a report path, so the test and exception are read from the per-class HTML reports and printed as `::error::` annotations.
- **Count device-lane flakes over every ATTEMPT, not every run.** A rerun replaces the run's conclusion, so `gh run list` shows a rerun-to-green run as green (or as cancelled, when the rerun was superseded): two of the three failures first reported for 2026-11-16 were invisible that way. List jobs with `gh api "repos/pyreon/pyreon/actions/runs/<id>/jobs?filter=all"` and read `run_attempt` and `conclusion` per job; the per-test assertion is in the `android-connected-reports` artifact of the failed attempt. Measured this way for 2026-11-11..16: 56 Android attempts reached a verdict, 13 red, 12 of them instrumented-test failures with three harness causes (soft keyboard, the old Compose rule's dispatcher, unawaited shell commands): see "Device-only gotchas" 8–10 in `.agents/guides/multiplatform/README.md`. Check a new intermittent failure against those three before reading the app.
- **The simulator's cold start costs about the same wherever it lands.** Booting right after checkout slows `bun install` to 150–265 s and the lib build to 85–200 s (21–32 s and 52–80 s on the same image with no simulator). Booting after them was measured (PR #4487, run 43217949673): install 30 s and lib 60 s, but the Swift unit tests doubled to 4.3 min and the first `xcodebuild test` waited 300 s for the device before its first test (66 s in the old order). Job start to the end of the todomvc UITest was 15.5 min against 13.6–17.2 (median 15.1): a tie, so the boot stays first. `simctl bootstatus` is not test-readiness (it returned after 93 s). `native-ios-uitest.ts` prints the seconds from starting xcodebuild to the first test in each suite's summary.
- **The iOS apps build through one workspace** (`$PYREON_IOS_WS`, written by the job) **into one DerivedData** (`$PYREON_IOS_DD`), so `PyreonRuntime` and `PyreonRouter` compile once per job instead of once per app (36–81 s each). A shared `-derivedDataPath` with `-project` builds does not do this: the package tasks are keyed on the project that builds them, so every project switch recompiles them (probed finance → todomvc → finance: `PyreonRuntime.o` rewritten each time through `-project`, untouched through the workspace). Nothing is cached across runs, so there is no eviction or invalidation rule; reuse within the job is decided by the build system's input signatures.
- **The Android lane usually resolves its Gradle dependencies from the network.** The `gradle-deps-*` cache has one writer (the nightly on `main`) and the 10 GB budget evicts by last use: the entry saved by the 2026-11-11 nightly was gone 9.5 hours later, and five of five PR runs inspected on 2026-11-11/12 missed it (the first `assembleDebug` then spends about 2.5 min resolving). So every `assembleDebug` runs through `scripts/native-gradle.sh`, which retries a failed dependency download (and nothing else: a compile error or failed task exits at once) up to three attempts with a `::warning::` per retry. The pinned Gradle zip cache is keyed on `GRADLE_VERSION`, not on the workflow's hash, so a workflow edit does not make every PR save its own 144 MB copy.
- **Timeouts are sums of measured parts.** The job timeouts in `native-device.yml` state their derivation (slowest green value of each step, plus margin), and every device step has its own `timeout-minutes` at 1.5–2× its slowest green run so a hang fails in that step. Re-derive both when a suite grows; do not raise a number without the table.
- **System sheets are remote views.** A PHPicker or document-picker button is in the accessibility tree before the out-of-process picker accepts touches, so a single tap sent the moment it exists can be dropped (the picker stays open and the test blames the delegate). Tap until the control is gone, bounded, as `dismissSystemPicker` in `PyreonCounterUITests.swift` does; the assertion on the app's own state stays unchanged.
- Deliver deep links through `XCUIDevice.shared.system.open(URL)` in XCUITest, then assert both cold and warm routes. Safari's address bar and confirmation sheet are unrelated dependencies and must not decide whether URL handling is tested. A failed route assertion stays a hard failure.
- `docs.yml` — concurrency cancels superseded PR builds but never a running `main` deploy (pending ones coalesce to the latest); cancelling the running deploy left pyreon.dev un-deployed for 7.5 h on 2026-11-10 while each run waited about an hour for a runner. Docs SSG and Atlas build on relevant PRs; deploy only from `main` (push, a daily 00:05 UTC schedule that publishes future-dated blog posts on their date, or a manual dispatch). Upload and deploy share one condition, `event_name != 'pull_request' && ref == main`; a PR never deploys. Linux command deadlines cover install (10m), docs (8m), and Atlas (3m), below the 25m job backstop. Explicit Bash preserves the failed producer's status through `tee`. Always upload phase logs and the SSG error artifact before the job backstop; a timed-out command must fail, and a successful rerun does not establish the earlier stall's cause. Google Fonts self-hosting shares a 60s abort deadline across CSS and font bodies. The site publishes the repo-root generated `llms.txt` / `llms-full.txt` at its root (`docs/vite-plugins/publish-llms-txt.ts`); a step fails the build unless `docs/dist` holds both byte-identical, and both files are in the workflow's path filters so a manifest-only change redeploys them. `llms.txt` is an [llmstxt.org](https://llmstxt.org/) index (H1, `>` summary, `##` sections of `- [title](url): notes` links; `gen-docs` rejects any other shape via `checkLlmsTxtShape`), and the long-form reference lives in `llms-full.txt`. The build uploads `dist` (before Atlas and the showcase are added) for the separate `lighthouse` job (Gate reference, "Lighthouse check"), which `deploy` does not wait for.
