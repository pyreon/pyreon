'@pyreon/compiler': patch
---

A prop-derived `const` whose initializer creates state anywhere in it is no longer inlined at its JSX use sites. `const count = props.shared ?? signal(0)` (the standalone `<Example>` counter in the docs) was re-evaluated at every use, so with no `shared` prop each read created a new signal and the counter never updated. The check used to look only at the initializer's outermost call; it now covers a stateful call (`signal`, `computed`, `effect`, `batch`, `defineStore`, any `useX` / `createX`) on either side of `??` / `||` / `&&`, in a ternary branch, a call argument, an object, array or template literal, or a callback the initializer calls, plus any `new` other than `Date` / `URL` / `RegExp` / `Intl.*`, a class expression, a write, and `await` / `yield`. Such a `const` keeps the value it had at setup.

Two related changes users could notice. A pure prop-derived `const` (`const label = props.label`) is now inlined on every element, not only on template elements: a handler, `ref` or render prop on a component, a childless or spread-carrying element, and a component's function child (`<Box>{() => label}</Box>`) now read the current prop instead of the value at setup. And a use where inlining would change what a name refers to keeps the `const`: `const lbl = props.label + tag` used inside `items.map((tag) => …)` used to read the map parameter. Both compiler backends; the native one also now inlines the initializer shapes it used to skip (`new`, tagged templates, comma expressions, spread arguments), matching the JS backend.
