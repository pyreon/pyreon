---
'@pyreon/storage': patch
---

A full storage no longer makes `useStorage` forget what is stored (#4812). Availability is now checked with a read, not a test write. On a localStorage or sessionStorage where every write throws `QuotaExceededError`, `useStorage` / `useSessionStorage` return the stored value instead of the default, `.set()` updates the signal and reports the failure to `onError` (it was silently dropped), and `.remove()` deletes again. A storage that recovers space persists the next write; before, it stayed disabled for the life of the binding. The same rule now holds for every backend. A failed write or remove never changes the stored value (the signal still shows the new value) and always reaches `onError`. `onError` fires on every failed write, so a storage that can never be written (legacy Safari private mode) reports every `.set()`: throttle user-facing notifications. A cookie write or delete the browser refuses no longer throws out of `.set()` / `.remove()`, and a cookie the browser silently drops (over ~4 KB, `sameSite: 'none'` without `secure`) is detected by reading it back and reported. A cookie read the browser refuses falls back to the default. An IndexedDB write or delete is reported failed when its transaction aborts, which is how a quota failure arrives, not only when the request errors, and a request error reaches `onError` under its real name (`ConstraintError`, not a synthetic `UnknownError`). `removeStorage(key, { type: 'indexeddb' })` without a live binding now deletes the key (it deleted nothing); it takes `dbName` / `storeName` for a non-default database. `removeStorage(key, { type: 'cookie' })` without a binding no longer throws in a document that refuses cookies. A custom backend's failed `remove()` and IndexedDB's failed delete are reported instead of swallowed.
