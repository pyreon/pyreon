zero follows Vite's resolved `base`, with two explicit bases: a ROUTE base (always a path: `zero({ base })`, else Vite's base when it is a path, else `/`) for router links, `__ZERO_BASE__`, the dev and production servers' routing and the PWA scope, and an ASSET base (Vite's resolved base, which may be a CDN URL) for chunks, SSG modulepreloads, `cssMode: 'asset'` stylesheets, OG images and self-hosted fonts. `vite build --base /x/`, a programmatic `build({ base })` or `vite.config.base` no longer leave any of those under `/`, and a CDN base no longer becomes a `/https://…` router base. The dev server now renders pages under a base (it rendered the loading fallback, with unprefixed links). Precedence: an explicit `zero({ base })` wins, then Vite's base, then `/`; zero's plugin no longer returns its default `/` over a Vite-level base. zero's `<Link>` / `createLink` / `useLink().href()` now render an internal root-relative href with the router base, like `<RouterLink>`. The internal `argvHasBaseFlag` helper is removed. loom's static-site build no longer passes its `--base` to zero separately.

Upgrade: manual — a `base` in `vite.config.ts` or a programmatic `build({ base })` that zero used to IGNORE (it forced `/`; `vite build --base` reached only the assets) now takes effect: assets move under it, and when it is a path the routes do too. Remove it if you relied on it being ignored. A relative `./` base now stops ssg/ssr/isr builds with an error (it only ever worked at the root; use a path or a CDN URL, or `mode: 'spa'`), and `zero({ pwa })` needs a path base. `zero({ base })` must now be a root-relative path (a missing trailing slash is added): a CDN URL, `./` or `docs/` there is rejected at config time — move it to `vite.config.base`. (It never worked: it became the router base, `/https://cdn…/about`, or never matched a request path.) An app that set a different `vite.config.base` and `zero({ base })` gets `zero({ base })` for both, as before for assets. Code importing the internal `argvHasBaseFlag` must stop.
